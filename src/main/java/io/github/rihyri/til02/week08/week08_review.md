# Week 08 - 학습 및 프로젝트 회고

<br>

8주차에는 Spring AOP와 리팩토링, 단위 테스트 및 API 테스트, 백엔드 보안 점검에 대해 학습했다.

이전까지는 데이터베이스와 트랜잭션을 중심으로 기능을 정상적으로 구현하고, 데이터를 안정적으로 처리하는 방법에 집중했다.

하지만 이번 수업에서는 기능이 정상적으로 동작하더라도 코드의 구조가 복잡하거나 테스트하기 어렵다면 유지보수 과정에서 문제가 발생할 수 있다는 점을 알게 되었따.

특히 **기능 구현에서 끝나는 것이 아니라, 코드의 책임을 분리하고 테스트와 보안까지 고려하는 것이 중요하다**는 점이 인상 깊었다.

<br>

### Spring AOP와 프록시 기반 동작

이번 주에는 AOP를 통해 여러 서비스에서 반복되는 로깅이나 실행 시간 측정 등의 공통 기능을 분리하는 방법을 학습했다.

처음에는 `@Before`, `@After`, `@Around`와 같은 어노테이션을 사용하면 공통 기능이 실행된다는 점은 이해했지만, 실제로 어떤 원리로 동작하는지 파악하기 어려웠다.

특히 **프록시(Proxy)** 라는 개념이 익숙하지 않아 실제 객체와 프록시 객체의 역할을 구분하는 과정이 헷갈렸다.

하지만 프록시가 실제 객체를 대신하여 요청을 받고, 부가 기능을 수행한 뒤 대상 메서드를 호출한다는 흐름을 학습하면서 AOP의 동작 원리를 조금 더 이해할 수 있었다.

또한 같은 클래스 내부에서 메서드를 직접 호출하면 프록시를 거치지 않아 AOP가 적용되지 않을 수 있다는 점도 알게 되었다.

### 리팩토링과 클린 코드

리팩토링을 학습하면서 단순히 코드의 길이를 줄이거나 중복을 제거하는 것만이 좋은 코드의 기준은 아니라는 점을 알게 되었다.

기존에는 Service에서 데이터를 조회하고 상태를 검증한 후 변경하는 방식이 자연스럽다고 생각했다.

하지만 빈약한 도메인 도메인과 풍부한 도메인 모델을 비교하면서, Entity가 자신의 상태와 관련된 비즈니스 규칙을 직접 관리하도록 설계할 수 있다는 점이 인상 깊었다.

특히 Setter를 통해 상태를 변경하는 대신 cancelOrder()와 같이 의미 있는 메서드를 제공하면 코드의 의도가 명확해지고 잘못된 상태 변경도 방지할 수 있다는 점을 이해했다.

**좋은 코드는 단순히 짧은 코드가 아니라, 각 클래스와 메서드의 책임이 명확하게 드러나는 코드**라는 점을 배웠다.

### 단위 테스트와 API 테스트

JUnit5와 Mockito를 활용하여 테스트 코드를 작성하는 방법을 학습했다.

이전에는 Swagger 등을 이용해 API를 직접 호출하고 결과를 확인하는 방식에 익숙했기 때문에, 테스트 코드를 별도로 작성해야 하는 이유를 깊이 생각하지 못했다.

하지만 단위 테스트를 학습하면서 기능이 정상적으로 동작하는지 반복적으로 검증할 수 있고, 리팩토링 이후에도 기존 기능이 유지되는지 확인할 수 있다는 점을 알게 되었다.

특히 Mockito를 사용하면 실제 데이터베이스가 없어도 Mock 객체를 통해 Service의 비즈니스 로직을 독립적으로 검증할 수 있다는 점이 흥미로웠다.

처음에는 `@Mock`, `@InjectMocks`, `when()`, `verify()`의 역할을 구분하는 것이 익숙하지 않았지만, 테스트 대상과 외부 의존성을 분리한다는 개념을 중심으로 이해하려고 했다.

또한 정상적인 요청뿐 아니라 예외 상황과 경계값까지 테스트해야 한다는 점에서, **테스트는 단순히 성공 여부를 확인하는 작업이 아니라 예상하지 못한 상황을 미리 검증하는 과정**이라는 것을 알게 되었다.

### 백엔드 보안과 AI 기반 보안 점검

SQL Injection, CSRF, CORS, 백도어 등 백엔드에서 발생할 수 있는 보안 문제에 대해 학습했다.

그동안은 API가 정상적으로 요청을 처리하는지에 집중했지만, 이번 수업을 통해 기능이 정상적으로 동작하는 것과 안전하게 동작하는 것은 다르다는 점을 알게 되었다.

특히 CSRF와 CORS는 이름도 비슷하고 모두 웹 보안과 관련된 개념이어서 초기에는 차이를 이해하기 어려웠다.

하지만 CSRF는 사용자가 의도하지 않은 요청이 실행되는 공격이고, CORS는 브라우저에서 서로 다른 출처 간 접근을 제어하기 위한 메커니즘이라는 점을 구분하면서 개념을 정리할 수 있었다.

또한 AI를 활용하면 코드에서 의심스러운 부분을 찾고 수정 방향을 검토하는 데 도움을 받을 수 있지만, AI가 제안한 결과를 그대로 신뢰해서는 안 된다는 점도 중요하게 느껴졌다.

**보안 점검에서는 취약점의 발생 원리를 이해하고, 실제 문제가 존재하는지 직접 검증하는 과정이 필요하다**는 점도 배웠다.

<br>

이번 8주차에는 애플리케이션의 기능 구현뿐 아니라 코드의 구조와 품질, 테스트 및 보안까지 폭넓게 학습할 수 있었다.

특히 AOP와 리팩토링을 통해 책임을 분리하는 방법을 이해하고, 테스트 코드가 안전한 코드 변경을 위한 중요한 기반이라는 점을 알게 되었다.

아직 프록시의 세부 동작이나 Mockito를 활용한 테스트 작성, Spring Security의 보안 설정 등은 추가적인 실습이 필요하다고 느낀다.

앞으로는 기능을 구현한 뒤 정상적으로 실행되는지만 확인하는 것이 아니라, **코드의 구조가 적절한지, 예외 상황에서도 올바르게 동작하는지, 보안상 문제가 없는지 함께 확인하는 습관** 또한 가져야겠다.
