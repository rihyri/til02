## 1. Spring AOP

<br>

AOP(Aspect-Oriented Programming)는 관점 지향 프로그래밍으로, 로깅이나 실행 시간 측정, 보안과 같이 여러 기능에 공통으로 사용되는 **횡단 관심사(Cross-Cutting Concern)** 를 핵심 비즈니스 로직과 분리하는 프로그래밍 방식이다.

AOP를 활용하면 서비스마다 반복되는 공통 코드를 줄이고, 비즈니스 로직에 집중할 수 있다.

<br>

### Advice 종류

- `@Before` : 대상 메서드 실행 전
- `@After` : 메서드가 정상 또는 예외로 종료된 후
- `@AfterReturning` : 정상적으로 반환된 후
- `@AfterThrowing` : 예외가 전파될 때
- `@Around` : 메서드 실행 전후를 감싸서 처리

특히 `@Around`는 `ProceedingJoinPoint`의 `proceed()`를 이용해 실제 메서드를 실행하고, 실행 시간 측정이나 결과 처리 등의 기능을 구현할 수 있다.

<br>

### Pointcut 표현식

Pointcut은 공통 기능을 적용할 대상을 지정하는 조건이다.

- `execution()` : 메서드의 이름, 반환 타입, 파라미터 등을 기준으로 선택
- `within()` : 특정 클래스 또는 패키지를 기준으로 선택
- `@annotation()` : 특정 어노테이션이 선언된 메서드를 선택

<br>

### 프록시 기반 원리

Spring AOP는 기본적으로 **프록시(Proxy)**를 이용해 동작한다.

```aiignore
Controller
    ↓
Proxy
    ├── Advice 실행
    ↓
Target Service
    └── 실제 비즈니스 로직
    ↓
Proxy
    └── 후처리
    ↓
Controller
```

프록시는 실제 객체를 대신하여 요청을 받고, 공통 기능을 수행한 뒤 대상 객체의 메서드를 호출한다.

**주의할 점은 같은 객체 내부에서 메서드를 직접 호출하는 Self-Invocation의 경우, 프록시를 거치지 않아 AOP가 적용되지 않을 수 있다는 것이다.**

## 2. 리팩토링과 클린 코드

<br>

리팩토링(Refactoring)은 **외부에서 관찰되는 프로그램의 동작을 유지하면서 내부 코드 구조를 개선하는 작업**이다.

새로운 기능을 구현하는 것이 아니라 코드의 가독성과 유지보수성, 확장성을 높이는 것이 목적이다.

<br>

### 코드 스멜 (Code Smell)

코드 스멜은 코드에 개선이 필요할 수 있음을 나타내는 징후이다.

    <thead>

    </thead>
    <tbody>

            <td>중복 코드</td>
            <td>공통 메서드 추출</td>
        </tr>
        <tr>
            <td>긴 메서드</td>
            <td>책임에 따라 메서드 분리</td>
        </tr>

        </tr>

</table>

<br>

### 대표적인 리팩토링 기법

#### 1. 메서드 추출 (Extract Method)

반복되거나 독립적인 의미를 가진 코드를 별도의 메서드로 분리한다.

#### 2. 네이밍 개선 (Rename)

변수와 메서드의 역할을 구체적으로 표현하여 코드를 쉽게 이해할 수 있도록 한다.

#### 3. 책임 분리

하나의 클래스가 너무 많은 역할을 수행하지 않도록 책임을 나누고 응집도를 높인다.

<br>

### 빈약한 도메인 모델과 풍부한 도메인 모델

빈약한 도메인 모델(Anemic Domain Model)은 Entity가 주로 데이터를 보관하고, 비즈니스 규칙을 Service에서 처리하는 구조이다.

반면 풍부한 도메인 모델(Rich Domain Model)은 Entity가 자신의 상태와 관련된 비즈니스 규칙을 직접 관리한다.

예를 들어 주문 취소 기능을 구현할 때 다음과 같이 작성할 수 있다.

```java
public void cancelOrder() {
    if (this.status != OrderStatus.PENDING) {
        throw new IllegalStateException("취소할 수 없는 주문입니다.");
    }
    
    this.status = OrderStatus.CANCELED;
}
```

이렇게 구현하면 주문 상태를 변경하는 규칙이 Entity 내부에 모이므로 외부에서 잘못된 상태 변경을 수행할 가능성을 줄일 수 있다.

**리팩토링에서 중요한 것은 단순히 코드를 짧게 만드는 것이 아니라, 책임을 명확히 분리하고 변경에 유연한 구조를 만드는 것이다.**

## 3. 단위 테스트와 API 테스트

<br>

테스트는 애플리케이션이 요구사항에 맞게 동작하는지 검증하고, 변경으로 인해 기존 기능이 잘못 동작하는 회귀 문제를 방지하는 과정이다.

<br>

### 단위 테스트 (Unit Test)

단위 테스트는 메서드나 클래스와 같은 작은 단위의 기능이 예상한 대로 동작하는지 검증한다.

외부 의존성을 분리하면 데이터베이스나 네트워크 환경에 영향을 받지 않고 비즈니스 로직을 빠르게 검증할 수 있다.

<br>

### JUnit 5

JUnit 5는 Java 애플리케이션의 테스트를 작성하고 실행하기 위한 테스트 프레임워크이다.

### 테스트 작성 패턴

#### AAA 패턴
```aiignore
Arrange → 테스트 데이터 준비
Act     → 테스트 대상 실행
Assert  → 결과 검증
```

#### Given-When-Then 패턴

```aiignore
Given   → 주어진 조건
When    → 수행한 동작
Then    → 기대한 결과
```

두 패턴 모두 테스트의 준비, 실행, 검증 단계를 구분하여 가독성을 높이는 데 도움을 준다.

<br>

### Mockito

Mockito는 실제 객체 대신 Mock 객체를 만들어 외부 의존성을 제어하는 테스트 도구이다.

- `@Mock` : Mock 객체 생성
- `@InjectMocks` : 테스트 대상에 Mock 의존성 주입
- `when().thenReturn()` : 특정 호출에 대한 반환값 설정
- `verify()` : 메서드 호출 여부 검증

Mock을 활용하면 실제 데이터베이스를 사용하지 않고도 Service의 비즈니스 로직을 독립적으로 테스트할 수 있다.

<br>

### 테스트 케이스 설계

테스트에서는 정상적인 상황뿐 아니라 예외 상황과 경계값도 확인해야 한다.

예를 들어 재고가 10개인 상품을 주문한다면 다음과 같은 경우를 검증할 수 있다.

- 주문 수량 0개: 예외 발생
- 주문 수량 1개: 정상 주문
- 주문 수량 10개: 정상 주문 및 재고 소진
- 주문 수량 11개: 재고 부족 예외 발생

<br>

### API 테스트

API 테스트는 HTTP 요청부터 응답까지의 동작을 검증한다.

주요 검증 항목은 다음과 같다.

- HTTP 상태 코드
- 응답 JSON의 구조 및 데이터
- 요청 파라미터와 입력값 검증
- 예외 발생 시 오류 응답

단위 테스트가 개별 기능의 정확성을 검증한다면, API 테스트는 **외부에서 제공되는 API가 기대한 계약대로 동작하는지** 확인하는 데 중점을 둔다.

## 4. 백엔드 보안과 AI 기반 보안 점검

백엔드 보안은 외부 요청으로부터 시스템과 데이터를 보호하기 위해 인증, 인가, 입력값 검증 및 접근 제어 등을 적용하는 과정이다.

프론트엔드에서 입력값을 검증하더라도 클라이언트는 HTTP 요청을 직접 변경할 수 있기 때문에, 서버에서도 반드시 검증해야 한다.

<br>

### 인증과 인가

- **인증 (Authentication)** : 사용자가 누구인지 확인하는 과정
- **인가 (Authorization)** : 해당 사용자가 특정 작업을 수행할 권한이 있는지 확인하는 과정

로그인에 성공한 사용자라고 해서 다른 사용자의 정보를 조회하거나 수정할 수 있는 것은 아니다.

<br>

### SQL Injection

SQL Injection은 사용자 입력값이 SQL 문자열에 직접 결합되면서 쿼리의 구조가 변경되는 취약점이다.

이를 예방하기 위해 `PreparedStatement`나 파라미터 바인딩을 사용해야 한다.

```java
String sql = """
        SELECT id, name, price
        FROM security_products
        WHERE name = ?
        """;
```

사용자 입력을 SQL 구문과 분리하면 입력값이 데이터로 처리되어 쿼리 구조를 변경하지 못하도록 막을 수 있다.

<br>

### CSRF와 CORS

CSRF(Cross-Site Request Forgery)는 공격자가 사용자 인증 상태를 악용해, 사용자가 의도하지 않은 요청을 실행하도록 유도하는 공격이다.

CORS(Cross-Origin Resource Sharing)는 브라우저가 서로 다른 출처 간 리소스 접근을 허용할지 판단할 수 있도록 하는 메커니즘이다.

<table>
    <thead>
        <th>구분</th>
        <th>CSRF</th>
        <th>CORS</th>
    </thead>
    <tbody>
        <tr>
            <td>개념</td>
            <td>요청 위조 공격</td>
            <td>교차 출처 접근 제어</td>
        </tr>
        <tr>
            <td>주요 문제</td>
            <td>사용자 의도와 다른 요청 실행</td>
            <td>허용되지 않은 출처로 응답 노출</td>
        </tr>
        <tr>
            <td>대응</td>
            <td>CSRF 토큰, SameSite 정책</td>
            <td>허용할 Origin 제한</td>
        </tr>
    </tbody>
</table>

CSRF와 CORS는 목적이 다르므로, **CORS를 설정했다고 해서 CSRF 공격까지 방지되는 것은 아니다.**

<br>

### 백도어와 보안 설정

백도어(Backdoor)는 정상적인 인증이나 접근 제어를 우회하여 시스템에 접근할 수 있도록 만들어진 숨겨진 통로이다.

대표적으로 인증이 없는 관리 API, 하드코딩된 비밀번호, 운영 환경에 남아 있는 디버그 기능 등이 문제가 될 수 있다.

<br>

### AI를 활용한 보안 점검

AI는 코드의 취약점을 탐색하고 개선 방안을 제안하는 보조 도구로 활용할 수 있다.

```aiignore
보안 개념 이해
    ↓
점검 범위 설정
    ↓
AI를 활용한 코드 분석
    ↓
취약점 존재 여부 검증
    ↓
수정 및 회귀 테스트
```

다만 AI가 제안한 취약점이 실제로 존재하는지 개발자가 확인해야 하며, 민감한 인증 정보나 비밀번호를 AI에 그대로 전달하지 않도록 주의해야 한다.

## 5. 8주차 핵심 정리

<br>

이번 주의 주요 학습 내용을 정리하면 다음과 같다.

1. **Spring AOP** : 프록시를 활용하여 공통 기능과 비즈니스 로직을 분리한다.
2. **리팩토링** : 기존 동작을 유지하면서 코드의 가독성과 유지보수성을 개선한다.
3. **단위 테스트** : 작은 단위의 비즈니스 로직을 독립적으로 검증한다.
4. **API 테스트** : HTTP 요청과 응답이 기대한 계약을 만족하는지 확인한다.
5. **백엔드 보안** : 인증, 인가, 입력값 검증과 보안 설정을 통해 취약점을 예방한다.

8주차에는 기능을 구현하는 것에 더 나아가, **작성한 코드가 이해하기 쉽고, 테스트할 수 있으며, 안전하게 유지될 수 있는 구조인지 고민하는 과정**을 학습했다.

특히 AOP와 리팩토링을 통한 책임 분리, 테스트를 통한 동작 검증, 보안 점검을 통한 취약점 예방은 서로 독립적인 기술이 아니라 애플리케이션의 품질을 높이기 위해 함께 고려해야 하는 요소라는 점을 이해할 수 있었다.

<br>
