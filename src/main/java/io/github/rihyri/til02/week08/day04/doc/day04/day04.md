## 1. 백엔드 보안의 기초

<br>

### 1.1 보안 취약점이란?

`보안 취약점(Vulnerability)`이란 공격자가 시스템을 개발자의 의도와 다르게 사용하여 데이터를 유출하거나 변경하고, 서비스를 방해할 수 있게 만드는 코드 또는 설정의 약점이다.

일반적인 기능 테스트로는 **요청에 대해 기능이 정상 동작하는지**확인한다. 반면 보안 테스트는 **누가, 어떤 방법으로 요청했는지에 따라 기능의 실행을 허용해도 되는지** 확인한다.

예를 들어 회원 삭제 API가 정상 동작하더라도, 다른 사용자의 계정을 삭제할 수 있다면 보안 취약점이 존재하는 것이다.

보안 취약점은 크게 다음과 같이 구분할 수 있다.

<table>
    <thead>
        <th>구분</th>
        <th>설명</th>
        <th>예시</th>
    </thead>
    <tbody>
        <tr>
            <td>코드의 약점</td>
            <td>입력값이나 권한을 잘못 처리</td>
            <td>SQL Injection, 인가 누락</td>
        </tr>
        <tr>
            <td>설정의 약점</td>
            <td>서버나 프레임워크 설정을 과도하게 허용</td>
            <td>CORS 전체 허용, 관리 API 노출</td>
        </tr>
    </tbody>
</table>

<br>

### 1.2 백엔드 보안이 중요한 이유

프론트엔드에서 입력값을 검증하더라도 사용자는 Postman이나 별도의 HTTP 클라이언트로 서버에 직접 요청할 수 있다.

따라서 프론트엔드 검증만으로 데이터의 무결성과 안정성을 보장할 수 없다.

백엔드에서는 다음을 반드시 확인해야 한다.

- **인증 (Authentication) :** 요청을 보낸 사용자가 누구인지 확인한다.
- **인가 (Authorization) :** 해당 사용자에게 요청한 작업을 수행할 권한이 있는지 확인한다.
- **입력 검증 (Validation) :** 전달된 데이터가 서비스의 요구사항에 적합한지 확인한다.

특히 인증과 인가는 서로 다른 개념이다.

로그인에 성공한 사용자라도 다른 사람의 개인정보를 조회하거나 수정할 권한이 있는 것은 아니다.

<br>

### 1.3 신뢰 경계 (Trust Boundary)

신뢰 경계란 신뢰 수준이 서로 다른 영역 사이의 경계를 의미한다.

일반적인 백엔드 애플리케이션의 흐름은 다음과 같다.

```aiignore
브라우저 / 모바일 앱
        │
        ▼
  백엔드 서버
  ├── 인증
  ├── 인가
  └── 입력 검증
        │
        ▼
  DB / 내부 시스템
```

클라이언트에서 전달하는 값은 사용자가 언제든지 변경할 수 있으므로 신뢰해서는 안 된다.

백엔드는 외부 입력이 내부 시스템에 영향을 주기 전에 적절한 검증과 접근 제어를 수행해야 한다.

또한 DB도 완전히 신뢰할 수 있는 영역으로만 생각해서는 안 된다. 외부 API 응답, 저장된 사용자 데이터 등도 다시 사용할 때 검증이 필요할 수 있다.

<br>

### 1.4 동일 출처 정책 (SOP)

SOP(Same-Origin Policy)는 브라우저에서 다른 출처의 리소스에 접근하는 것을 제한하는 보안 정책이다.

출처(Origin)은 다음 세 요소로 결정된다.

```aiignore
Origin = Protocol + Host + Port
```

예를 들어 다음 주소는 서로 다른 출처에 해당한다.

```aiignore
https://shop.com
http://shop.com
https://shop.com:8080
```

프로토콜 또는 포트가 다르기 때문이다.

SOP는 일반적으로 다른 출처의 응답을 JavaScript가 읽는 것을 제한한다.

그러나 모든 교차 출처 요청 자체를 차단하는 것은 아니다.

특히 HTML Form과 같이 일부 요청은 서버에 전달될 수 있으며, 이러한 특성이 CSRF 공격과 연결된다.

## 2. AI를 이용한 보안 점검

<br>

### 2.1 AI와 개발자의 역할

AI 코딩 도구는 코드베이스에서 의심스러운 패턴을 빠르게 탐색하고 수정안을 제시할 수 있다.

그러나 AI가 발견한 문제가 실제 취약점인지는 개발자가 확인해야 한다.

        </tr>

            <td>수정 코드 초안 작성</td>
            <td>기존 기능 영향 분석</td>
        </tr>
        <tr>
            <td>테스트 코드 생성</td>

AI 보안 점검에서는 두 종류의 오류를 주의해야 한다.

- **오탐 (False Positive) :** 실제로 안전한 코드를 취약하다고 판단하는 경우
- **미탐 (False Negative) :** 실제 취약점이 존재하지만 발견하지 못 하는 경우

따라서 AI의 분석 결과는 최종 결론이 아닌 검토 대상이다.

<br>

### 2.2 보안 점검 5단계

1. **개념 이해 :** 공격 원리와 발생 조건을 먼저 이해한다.
2. **범위 설정 :** 점검할 패키지와 취약점 유형을 지정한다.
3. **AI 분석 :** 의심 코드의 위치와 수정안을 요청한다.
4. **검증 :** 실제로 취약점이 존재하는지 확인한다.
5. **수정 및 테스트 :** 취약점을 수정하고 회귀 테스트를 작성한다.

보안 점검은 단순히 취약한 코드를 찾아 수정하는 것으로 끝나지 않는다.

같은 문제가 다시 발생하지 않도록 테스트를 남기는 과정까지 포함해야 한다.

<br>

### 2.3 AI 보안 점검 프롬프트 예시

다음과 같은 형식으로 AI에게 코드 점검을 요청할 수 있다.

```aiignore

다음 패키지의 Controller, Service, Repository 코드를 점검해줘.

점검 기준:

2. 인증 및 인가 누락
3. 사용자 입력값 검증 누락

6. 민감정보가 노출되는 오류 응답

각 문제에 대해 다음 내용을 작성해줘.

- 파일 및 메서드 위치
- 문제가 되는 코드
- 취약점 발생 조건

```

이때 실제 비밀번호, API 키, 인증 토큰 등의 민감정보를 AI에게 그대로 제공하지 않도록 주의해야 한다.

## 3. SQL Injection

<br>

### 3.1 SQL Injection이란?

`SQL Injection`은 외부에서 전달된 문자열이 SQL 쿼리에 직접 결합되면서 쿼리의 구조나 의미가 변경되는 취약점이다.

대표적인 원인은 **사용자 입력값을 SQL 문자열에 그대로 연결하는 것**이다.

취약한 코드의 예시는 다음과 같다.

```JAVA
String sql =
    "SELECT * FROM security_products WHERE name = '"
    + name + "'";
```

이때 다음과 같은 문자열이 전달되었다고 가정한다.

```java
' OR '1' = '1
```

사용자 입력이 SQL 문자열에 결합되면 조건문이 항상 참으로 평가될 수 있다.

그 결과 원래 의도한 상품 한 개가 아니라 여러 상품이 조회될 수 있다.

<br>

## 3.2 파라미터 바인딩

SQL Injection을 방지하기 위해 `PreparedStatement` 기반의 파라미터 바인딩을 사용한다.

```java
String sql = """
        SELECT id, name, price
        FROM security_products
        WHERE name = ?
        """;
```

`?`는 실제 데이터가 전달될 위치를 나타낸다.

사용자가 전달한 문자열은 SQL 구문의 일부가 아니라 하나의 데이터 값으로 처리된다.

따라서 입력값에 SQL 예약어나 특수문자가 포함되어 있어도 쿼리 구조를 변경할 수 없다.

<br>

### 3.3 ORDER BY와 화이트리스트

파라미터 바인딩으로 모든 SQL 요소를 처리할 수 있는 것은 아니다.

특히 컬럼명, 테이블명, 정렬 방향 등은 일반적인 값 바인딩 대상이 아니다.

따라서 `ORDER BY`에 외부 입력을 사용하는 경우 허용 목록(Allowlist)을 활용한다.

```java
private static final Set<String> SORTABLE_COLUMNS = 
        Set.of("name", "price", "created_at");

if (!SORTABLE_COLUMNS.contains(sort)) {
    throw new IllegalArgumentException("허용되지 않은 정렬 기준")    
}
```

허용 목록에 포함된 컬럼만 사용하도록 제한하면 사용자가 의도하지 않은 SQL 구문을 삽입하는 위험을 줄일 수 있다.

<br>

### 3.4 입력값 검증

Spring에서는 Bean Validation을 사용하여 DTO에 검증 규칙을 선언할 수 있다.

```JAVA
@NotBlank
@Email
private String email;

@NotBlank
@Size(min = 8, max = 64)
private String password;
```

Controller에서 `@Valid`를 사용하면 요청 객체의 제약조건을 검증한다.

```java
@PostMapping("/users")
public void createUser(
        @Valid @RequestBody SecurityUserCreateRequest request
) {
    // 검증된 입력값 처리
}
```

다만 입력 검증은 파라미터 바인딩의 대체 수단이 아니다.

SQL Injection을 막기 위해서는 데이터 값의 파라미터 바인딩을 기본으로 적용해야 한다.

## 4. CSRF (Cross-Site Request Forgery)

<br>

### 4.1 CSRF란?

CSRF는 사용자가 특정 서비스에 로그인한 상태를 악용하여, 공격자가 사용자의 의도와 관계없이 요청을 실행하게 만드는 공격이다.

예를 들어 사용자가 쇼핑몰에 로그인한 상태에서 악성 사이트를 방문했다고 가정한다.

악성 사이트가 쇼핑몰의 개인정보 변경 API에 요청을 전송하고, 브라우저가 해당 요청에 로그인 세션 쿠키를 자동으로 포함한다면 서버는 이를 정상 사용자 요청으로 처리할 위험이 있다.

CSRF 공격에서 공격자는 반드시 서버의 응답을 읽을 필요는 없다.

**사용자가 원하지 않은 작업을 실행시키는 것 자체가 공격 목적**이기 때문이다.

<br>

### 4.2 CSRF 공격 흐름

```aiignore
① 사용자가 쇼핑몰에 로그인
           │
           ▼
② 브라우저에 세션 쿠키 저장
           │
           ▼
③ 사용자가 악성 사이트 방문
           │
           ▼
④ 악성 사이트에서 요청 전송
           │
           ▼
⑤ 브라우저가 조건에 따라 세션 쿠키 첨부
           │
           ▼
⑥ 서버가 요청을 처리할 위험 발생
```

여기서 중요한 점은 브라우저가 쿠키를 자동으로 전송할 수 있다는 것이다.

실제 쿠키 전송 여부는 SameSite 속성, 요청 유형, 브라우저 정책 등에 따라 달라진다.

<br>

### 4.3 CSRF 토큰으로 공격을 방어하는 원리

CSRF 토큰은 정상적인 클라이언트가 서버에서 제공한 검증값을 함께 전송하도록 하는 방식이다.

#### 정상 요청의 흐름

```aiignore
[사용자 브라우저]                  [백엔드 서버]
       │                               │
       │ ① 페이지 요청                 │
       ├──────────────────────────────►│
       │                               │
       │ ② CSRF 토큰 제공              │
       │◄──────────────────────────────┤
       │                               │
       │ ③ POST + CSRF 토큰            │
       ├──────────────────────────────►│
       │                               │
       │ ④ 토큰 검증                   │
       │                         유효한 토큰 확인
       │                               │
       │ ⑤ 요청 처리                   │
       │◄──────────────────────────────┤
```

정상적인 애플리케이션은 서버에서 발급한 토큰을 읽어 요청 파라미터나 헤더에 포함한다.

반면 공격자가 운영하는 다른 출처의 사이트는 일반적으로 SOP 때문에 정상 사이트의 토큰을 읽을 수 없다.

따라서 공격자는 사용자의 쿠키를 이용해 요청을 보낼 수 있더라도 유효한 CSRF 토큰까지 함께 전달하기 어렵다.

결과적으로 서버는 토큰이 없거나 유효하지 않은 요청을 거부한다.

**핵심은 쿠키와 CSRF 토큰의 전달 방식이 다르다는 것이다.**

- 세션 쿠키 : 브라우저가 조건에 따라 자동 전송
- CSRF 토큰 : 정상 애플리케이션이 요청에 명시적으로 포함
- 서버 : 전달된 토큰이 유효한지 검증

단, CSRF 토큰을 브라우저가 어떤 방식으로 보관하고 전달하는지는 애플리케이션의 구현에 따라 달라질 수 있다.

<br>

### 4.4 Spring Security의 CSRF 보호

Spring Security는 기본적으로 상태를 변경하는 HTTP 요청을 CSRF 검증 대상으로 처리한다.

```JAVA
http.csrf(Customizer.withDefaults());
```

일반적으로 유효한 토큰 없이 POST 요청을 보내면 403 Forbidden 응답이 반환된다.

SPA 환경에서는 `CookieCsrfTokenRepository`를 사용할 수 있다.

이 경우 `XSRF-TOKEN` 쿠키와 `X-XSRF-TOKEN` 헤더를 활용할 수 있지만, Spring Security 버전에 따라 토큰 로딩과 요청 처리 방식에 추가 설정이 필요할 수 있다.

CSRF를 무조건 비활성화하는 것은 적절하지 않다.

브라우저가 인증 정보를 자동으로 전송하는지, 어떤 인증 방식을 사용하는지 확인한 후 결정해야 한다.

예를 들어 JWT를 사용하더라도 JWT를 쿠키에 저장하고 자동 전송한다면 CSRF 위험을 고려해야 한다.

<br>

### 4.5 SameSite 쿠키

SameSite는 다른 사이트에서 시작된 요청에 쿠키를 전송할지 제어하는 속성이다.

<table>
    <thead>
        <th>옵션</th>
        <th>설명</th>
    </thead>
    <tbody>
        <tr>
            <td>Strict</td>
            <td>다른 사이트에서 시작된 요청에 쿠키 전송을 강하게 제한</td>
        </tr>
        <tr>
            <td>Lax</td>
            <td>일반적인 교차 사이트 하위 요청은 제한하고 일부 최상위 페이지 이동은 허용</td>
        </tr>
        <tr>
            <td>None</td>
            <td>교차 사이트 쿠키 전송을 허용하며 Secure 속성이 필요</td>
        </tr>
    </tbody>
</table>

SameSite는 CSRF 방어에 도움이 되지만, CSRF 토큰과 같은 다른 방어 기법을 대신하는 것으로 생각해서는 안 된다.

<br>
<hr>

### 5. CORS (Cross-Origin Resource Sharing)

<br>

## 5.1 CORS란?

CORS는 서버가 특정 출처의 브라우저 스크립트에 교차 출처 응답을 읽는 권한을 부여하는 메커니즘이다.

SOP가 다른 출처의 응답 접근을 제한하는 정책이라면, CORS는 필요한 출처에 한해 제한을 완화하는 방식이다.

예를 들어 다음 두 서버가 있다고 가정한다.

```aiignore
* Frontend
http://localhost:3000

* Backend
http://localhost:8080
```

두 주소는 포트가 다르므로 서로 다른 출처이다.

프론트엔드가 백엔드 API를 호출하고 응답을 읽으려면 적절한 CORS 설정이 필요하다.

<br>

### 5.2 주요 CORS 응답 헤더

<table>
    <thead>
        <th>헤더</th>
        <th>역할</th>
    </thead>
    <tbody>
        <tr>
            <td>Access-Control-Allow-Origin</td>
            <td>응답 읽기를 허용할 출처</td>
        </tr>
        <tr>
            <td>Access-Control-Allow-Methods</td>
            <td>허용할 HTTP 메서드</td>
        </tr>
        <tr>
            <td>Access-Control-Allow-Headers</td>
            <td>허용할 요청 헤더</td>
        </tr>
        <tr>
            <td>Access-Control-Allow-Credentials</td>
            <td>인증 정보가 포함된 요청에 대한 응답 접근 허용</td>
        </tr>
        <tr>
            <td>Access-Control-Max-Age</td>
            <td>Preflight 결과를 캐시할 수 있는 시간</td>
        </tr>
    </tbody>
</table>

인증 정보가 포함된 CORS 요청을 허용할 때는 접근 가능한 출처를 정확히 제한하는 것이 중요하다.

<br>

### 5.3 안전하지 않은 CORS 설정

```java
registry.addMapping("/**")
        .allowedOriginPatterns("*")
        .allowedMethods("*")
        .allowCredentials(true);
```

위 설정은 모든 출처 패턴을 허용하면서 인증 정보가 포함된 요청의 응답 접근도 허용한다.

의도하지 않은 외부 사이트에 민감한 응답이 노출될 위험이 있다.

<br>

### 5.4 안전한 CORS 설정

```java
CorsConfiguration config = new CorsConfiguration();

config.setAllowedOrigins(
        List.of("http://localhost:3000")      
);

config.setAllowedMethods(
        List.of("GET", "POST")
);

config.setAllowCredentials(true);
```

실제로 필요한 출처와 HTTP 메서드만 명시적으로 허용한다.

개발 환경과 운영 환경에서 허용할 출처가 다르다면 환경별 설정 파일이나 환경 변수를 사용하여 관리하는 것이 좋다.

<br>

### 5.5 단순 요청과 Preflight 요청

브라우저는 교차 출처 요청을 보낼 때 요청 조건에 따라 Preflight 요청을 먼저 전송할 수 있다.

<br>

#### 단순 요청 (Simple Request)
특정 HTTP 메서드와 헤더 조건을 만족하는 요청은 별도의 Preflight 없이 바로 전송된다.

이후 브라우저가 응답의 CORS 헤더를 확인한다.

#### Preflight 요청

PUT, DELETE 등의 메서드나 특정 커스텀 헤더, `application/json`과 같은 Content-Type을 사용하는 교차 출처 요청은 일반적으로 Preflight가 필요하다.

```aiignore
브라우저
   │
   │ OPTIONS 요청
   ▼
백엔드 서버
   │
   │ 허용 메서드 / 헤더 응답
   ▼
브라우저
   │
   │ 실제 POST 요청
   ▼
백엔드 서버
```

Preflight는 본 요청을 보내기 전에 해당 교차 출처 요청이 허용되는지 확인하는 과정이다.

다만 CORS는 브라우저의 보안 정책이므로 Postman이나 서버 간 요청에 대한 접근 제어 수단으로 사용할 수 없다.

<br>

### 5.6 CSRF와 CORS의 차이

<table>
    <thead>
        <th>구분</th>
        <th>CSRF</th>
        <th>CORS</th>
    </thead>
    <tbody>
        <tr>
            <td>정체</td>
            <td>공격 기법</td>
            <td>브라우저의 교차 출처 접근 제어 메커니즘</td>
        </tr>
        <tr>
            <td>핵심 위험</td>
            <td>사용자 의도와 다른 요청 실행</td>
            <td>허용되지 않아야 할 출처에 응답 노출</td>
        </tr>
        <tr>
            <td>주요 방어</td>
            <td>CSRF 토큰, SameSite</td>
            <td>허용할 Origin을 제한</td>
        </tr>
        <tr>
            <td>핵심 질문</td>
            <td>이 요청은 사용자가 의도한 것인가?</td>
            <td>이 출처가 응답을 읽어도 되는가?</td>
        </tr>
    </tbody>
</table>

CSRF와 CORS는 서로 다른 문제를 해결한다.

CORS는 엄격하게 설정했다고 해서 모든 CSRF 공격이 차단되는 것은 아니다.

반대로 CSRF 토큰을 적용했더라도 CORS 설정이 과도하게 열려 있다면 의도하지 않은 응답 노출 문제가 발생할 수 있다.

<br>

## 6. 백도어 (Backdoor)

<br>

### 6.1 백도어란?

백도어는 정상적인 인증 또는 접근 제어 절차를 우회하여 시스템에 접근할 수 있도록 만들어진 숨겨진 통로이다.

개발자가 테스트 편의를 위해 만든 기능이 운영 환경에 남아 있는 경우에도 문제가 발생할 수 있다.

대표적인 백도어 유형은 다음과 같다.

1. 인증 없이 호출할 수 있는 디버그 API
2. 코드에 하드코딩된 마스터 비밀번호
3. 의도하지 않게 추가된 악성 의존성

<br>

### 6.2 디버그 API 노출

예를 들어 다음과 같은 관리 API가 운영 환경에 남아 있다고 가정한다.

```JAVA
@GetMapping("/internal/debug/users")
public List<User> findAllUsers() {
    return userRepository.findAll();
}
```

이 API에 적절한 인증 및 인가가 없다면 개인정보가 외부로 노출될 수 있다.

또한 엔티티를 그대로 반환하면 비밀번호 해시 등 의도하지 않은 필드가 응답에 포함될 위험이 있다.

운영 환경에서는 불필요한 디버그 기능을 제거하고, 관리 기능이 필요하다면 별도의 인증 및 인가 정책을 적용해야 한다.

<br>

### 6.3 하드코딩된 마스터 비밀번호

```java
// 잘못된 인증 방식의 예
if ("master-password".equals(rawPassword)) {
    return true;
}
```

위와 같이 특정 비밀번호 하나로 모든 사용자 인증을 통과시키는 방식은 심각한 보안 문제가 된다.

정상적인 비밀번호 복구가 필요하다면 본인 확인 절차를 거치는 비밀번호 재설정 기능을 제공해야 한다.

<br>

### 6.4 의존성과 slopsquatting

AI가 실제로 존재하지 않는 라이브러리를 추천하는 경우가 있다.

공격자는 AI가 추천할 법한 패키지 이름을 미리 등록하고 악성 코드를 배포할 수 있다.

이러한 공격 방식을 **slopsquatting**이라고 한다.

라이브러리를 추가할 때는 다음 상황을 확인해야 한다.

- 공식 문서에서 안내하는 의존성인지
- 실제 배포 주체와 저장소가 신뢰할 수 있는지
- 이름이 유명한 라이브러리와 유사하지 않은지
- 프로젝트에서 사용하지 않은 의존성이 포함되어 있지 않은지 

AI가 생성된 의존성 목록도 검증 없이 사용해서는 안 된다.

<br>

## 7. 프로젝트 보안 점검

<br> 

기존 Spring Boot 프로젝트에서 우선적으로 점검해야 할 항목들을 정리한다.

<br>

### 7.1 하드코딩된 비밀번호

API Key, DB 비밀번호, JWT 서명키 등의 비밀정보를 코드에 직접 작성하지 않는다.

```java
external:
    api-key: ${EXTERNAL_API_KEY}
```

실행 환경의 환경 변수나 적절한 비밀정보 관리 시스템을 통해 주입한다.

<br>

### 7.2 비밀번호 저장

비밀번호는 평문으로 저장하지 않고 안전한 비밀번호 해싱 알고리즘을 사용해야 한다.

Spring Security에서는 `BCryptPasswordEncoder`를 사용할 수 있다.

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

String encodedPassword = passwordEncoder.encode(rawPassword);
```

BCrypt는 복호화하는 암호화 방식이 아닌, 비밀번호 검증에 적합한 단방향 해싱 방식이다.

<br>

### 7.3 인가 누락과 IDOR

IDOR(Insecure Direct Object Reference)는 사용자에게 권한이 없는 리소스에 직접 접근할 수 있는 취약점이다.

예를 들어 다음과 같은 API가 있다고 가정한다.

```aiignore
DELETE  /api/users/10
```

사용자 ID만 변경해 다른 사용자의 계정을 삭제할 수 있다면 인가 문제가 존재한다.

따라서 요청 파라미터로 전달된 사용자 ID를 신뢰하기보다, 서버에서 인증된 사용자 정보를 확인하고 해당 리소스에 접근할 권한이 있는지 검증해야 한다.

인증된 사용자 정보는 Spring Security의 SecurityContext 등에서 가져올 수 있다.

단순히 로그인 여부만 검사하는 것으로는 충분하지 않다.

<br>

### 7.4 예외 메시지를 통한 정보 노출

서버의 예외 메시지를 그대로 클라이언트에게 반환하면 내부 구현 정보가 노출될 수 있다.

예를 들어 SQL 쿼리, 테이블명, 내부 경로 등의 정보가 응답에 포함되지 않도록 주의해야 한다.

클라이언트에는 필요한 오류 코드와 일반적인 메시지를 전달하고, 서버 로그에는 문제 분석에 필요한 정보를 기록한다.

이때 서버 로그에도 비밀번호나 인증 토큰 등의 민감 정보가 포함되지 않도록 해야 한다.

<br>

### 7.5 보안 점검 체크리스트

- 외부 입력이 SQL 문자열에 직접 결합되지 않는가?
- 정렬 컬럼 등의 동적 SQL 요소를 허용 목록으로 제한했는가?
- 인증이 필요한 API에 인증 처리가 적용되어 있는가?
- CSRF 보호 설정이 인증 방식에 적합한가?
- CORS의 허용 출처가 최소한으로 설정되어 있는가?
- API Key와 비밀번호가 하드코딩되어 있지 않은가?
- 운영 환경에 불필요한 디버그 API가 존재하지 않는가?
- 의존성의 출처와 안정성을 확인했는가?
- 예외 응답이나 로그에 민감정보가 노출되지 않는가?
- 보안 문제가 재발하지 않도록 테스트를 작성했는가?

<br>

## 8. 핵심 정리

<br>

이번 학습에서는 백엔드 보안을 단순히 Spring Security 설정의 문제가 아니라 애플리케이션 전체에서 검증해야 하는 문제로 이해했다.

특히 다음 네 가지 원칙이 중요하다.

1. **클라이언트 입력을 신뢰하지 않는다.** 입력과 검증은 안전한 SQL 처리 방법을 적용한다.
2. **인증과 인가를 구분한다.** 로그인한 사용자라도 모든 데이터에 접근할 수 있는 것은 아니다.
3. **브라우저 보안 정책의 역할을 이해한다.** SOP, CORS, CSRF는 서로 다른 목적과 동작 원리를 가진다.
4. **AI의 분석 결과를 직접 검증한다.** 취약점 탐지부터 수정, 회귀 테스트까지 개발자가 책임져야 한다.

기능이 정상적으로 동작하는 것과 보안상 안전한 것은 서로 다르다.

백엔드 개발자는 기능 구현뿐 아니라 의도하지 않은 요청이 들어왔을 때 어떻게 처리되는지도 함께 고려해야 한다.

<br>
