# Week 08 - Day 04 회고

<br>

이번 수업에서는 AI를 활용한 백엔드 보암 점검 방법과 대표적인 웹 보안 취약점에 대해 학습했다.

지금까지는 API가 정상적으로 동작하고 원하는 데이터가 반환되는지를 중심으로 코드를 작성했다면, 이번에는 **정상적인 기능이라도 잘못된 요청이나 권한 없는 접근으로 인해 보안 문제가 발생할 수 있다**는 점을 배웠다.

특히 SQL Injection, CSRF, CORS의 개념과 방어 방법을 살펴보고, AI를 이용해 취약점을 탐지하더라도 개발자의 직접적인 검증이 필요하다는 것을 이해했다.

<br>

### 기능의 정상 동작과 보안은 별개이다.

기존에는 API가 요청에 맞는 응답을 반환하면 기능이 정상적으로 구현되었다고 생각했다.

하지만 인증되지 않은 사용자가 다른 사람의 데이터를 조회하거나 수정할 수 있다면, API가 기능적으로 정상 동작하더라도 안전하다고 볼 수 없다.

단순히 요청의 성공 여부를 확인하는 것을 넘어, **해당 요청이 허용되어야 하는 요청인지** 검증하는 과정이 필요하다는 점을 알게 되었다.

### SQL Injection은 쿼리 작성 방식에서 발생한다.

사용자 입력값을 SQL 문자열에 직접 연결하면 SQL Injection 취약점이 발생할 수 있다는 것을 배웠다.

`JdbcTemplate`의 파라미터 바인딩을 사용하면 외부 입력을 SQL 명령이 아닌 데이터로 처리할 수 있다.

또한 정렬 컬럼처럼 파라미터 바인딩을 적용하기 어려운 부분은 화이트리스트를 사용해야 한다는 점도 알게 되었다.

### CSRF와 CORS는 서로 다른 문제를 해결한다.

초기에는 CSRF와 CORS 모두 브라우저의 교차 출처 요청과 관련되어 있어 비슷한 개념이라고 생각했다.

하지만 학습을 진행하면서 두 개념의 목적이 다르다는 것을 알게 되었다.

CSRF는 사용자의 인증 상태를 악용하여 의도하지 않은 요청을 실행시키는 공격이고, CORS는 다른 출처의 스크립트에 응답 접근을 허용할지를 결정하는 메커니즘이다.

따라서 CORS를 제한한다고 CSRF 공격이 모두 차단되는 것은 아니다.

### CSRF 토큰의 동작 원리

이번 내용에서 가장 이해하기 어려웠던 부분은 CSRF 토큰을 이용한 방어 방식이었다.

브라우저가 요청에 쿠키를 자동으로 포함한다는 것은 이해했지만, CSRF 토큰을 추가하는 것이 왜 공격을 막을 수 있는지 처음에는 명확하지 않았다.

다시 정리하면서 정상적인 애플리케이션은 서버가 제공한 CSRF 토큰을 요청에 포함할 수 있지만, 다른 출처의 공격 페이지는 일반적으로 해당 토큰에 접근할 수 없다는 점이 핵심이라는 것을 알게 되었다.

또한 JWT를 사용하더라도 저장 및 전달 방식에 따라 CSRF 위험이 달라질 수 있다는 점도 새로웠다.

### 보안 설정의 적절한 범위 판단

CORS와 CSRF 설정은 코드를 작성하는 것보다 어떤 범위까지 허용해야 하는지 판단하는 것이 더 중요하게 느껴졌다.

개발 과정에서는 편의를 위해 모든 출처를 허용하거나 보안 기능을 비활성화하고 싶을 수 있지만, 이러한 설정이 운영 환경에 남으면 문제가 생길 수 있다.

따라서 설정의 의미와 적용 범위를 확인하는 습관이 필요하다고 느꼈다.

<br>

이번 학습을 통해 백엔드 개발에서 보안이 별도로 추가하는 기능이 아니라, 코드를 작성하는 과정에서 함께 고려해야 하는 기본적인 요소라는 것을 알게 되었다.

특히 이전까지는 정상적인 요청이 올바르게 처리되는지를 중심으로 생각했다면, 이제는 의도하지 않은 압력이나 권한이 없는 사용자의 요청이 들어왔을 때 어떻게 동작하는지도 확인해야 한다는 점을 배웠다.

앞으로는 AI가 제공하는 코드를 단순히 활용하는 데 그치지 않고, 직접 검증하고 안전성을 판단할 수 있는 백엔드 개발자가 되도록 해야겠다.
