# Week 08 - Day 02 회고. 리팩토링과 클린 코드

<br>

이번 수업에서는 리팩토링이 단순히 코드를 예쁘게 정리하는 과정이 아니라, **기존 동작을 유지하면서 유지 보수하기 좋은 구조로 개선하는 작업**임을 배웠다. 코드 스멜의 예시로 중복 코드, 긴 메서드, 모호한 네이밍, 한 곳에 집중된 책임을 살펴보고 메서드 추출과 책임 분리 방법을 정리했다.

주문 취소 예제를 통해 **빈약한 도메인 모델**과 **풍부한 도메인 모델**의 차이를 이해했다. Service에서 상태를 검사하고 Setter로 변경하던 방식에서, Entity의 `cancelOrder()` 메서드가 자신의 상태 변경 규칙을 책임지도록 바꾸는 과정을 확인했다.

- 좋은 네이밍은 별도 주석 없이도 코드의 의도를 전달하는 데 도움이 된다.
- DRY는 동일한 로직과 규칙의 중복을 줄여 수정 누락 가능성을 낮춘다.
- SRP는 책임을 분리하여 수정 시 영향 범위를 예측하기 쉽게 한다.
- 모든 로직을 Service에 둘 필요는 없으며, Entity 자신의 상태와 관련된 규칙은 Entity에 두는 방법도 고려할 수 있다.

<br>

앞으로도 코드를 작성하거나 수정할 때 메서드의 이름이 의도를 드러내는지, 중복된 규칙은 없는지, 책임이 한 클래스에 지나치게 몰여 있지 않은지 등을 점검해야겠다. 필요 이상으로 주석을 달기보다 코드 자체가 읽히도록 작성하되, 꼭 필요한 설계 의도는 주석으로 남길 예정이다.
