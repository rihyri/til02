# Week 08 - Day 03 회고

<br>

이번 수업에서는 `JUnit 5`와 `Mockito`를 활용한 단위 테스트, `Postman`과 `MockMvc`를 활용한 API 테스트 방법에 대해 학습했다.

기존에는 기능을 구현한 뒤 직접 실행하고 결과를 확인하는 방식에 익숙했지만, 이번 수업을 통해 테스트 코드를 작성하면 기능의 정상 동작 여부를 자동으로 검증할 수 있다는 점을 다시 한번 깨닫게 되었다.

<br>

### JUnit과 테스트 작성 패턴

JUnit의 `@Test`, `@BeforeEach`, `@DisplayName` 등을 활용해 테스트를 구성하는 방법을 학습했다.

또한 `AAA`와 `Given-When-Then` 패턴을 통해 테스트의 준비, 실행, 검증 단계를 구분하면 테스트의 목적을 명확하게 나타낼 수 있다는 점을 이해했다.

### Mockito를 이용한 의존성 제어

`@Mock`은 가짜 객체를 생성하고, `@InjectMocks`는 테스트 대상 객체에 필요한 Mock 의존성을 주입하는 역할을 한다.

`when().thenReturn()`으로 특정 메서드의 반환값을 설정하고, `verify()`로 메서드가 호출되었는지 확인할 수 있다는 점을 배웠다.

처음에는 단순히 메서드를 실행하고 결과를 확인하는 것이 테스트라고 생각했지만, 내부 의존성의 동작을 제어하는 과정도 중요하다는 것을 알게 되었다.

### API 테스트

Postman은 실행 중인 서버에 실제 요청을 전송하는 방식이고, MockMvc는 실제 서버 없이 HTTP 요청을 시뮬레이션하는 방식이라는 차이를 이해했다.

MockMvc를 활용하면 상태 코드와 JSON 응답을 자동으로 검증할 수 있어 반복적인 API 테스트에 효과적이라는 점을 알게 되었다.

<br>

가장 헷갈렸던 부분은 Mockito에서 사용하는 `when(), thenReturn(), verify()`의 역할이었다.

특히 `when()`을 작성하면 실제 Repository 메서드가 실행되는 것인지, 아니면 반환값만 미리 설정하는 것인지 구분하기 어려웠다.

또한 `@InjectMocks`를 통해 Mock 객체가 Service에 어떻게 주입되는지, Spring의 읜존성 주입과 어떤 차이가 있는지도 추가적인 이해가 필요했다.

테스트에서 엔티티 ID를 직접 설정하기 위해 사용하는 `ReflectionTestUtils.setField()` 역시 처음 접한 방식이었어서 사용 목적을 다시 확인할 필요가 있었다.

<br>

앞으로는 기능을 구현한 뒤 정상적인 결과만 확인하는 것이 아니라, 실패 상황과 경계값까지 고려하는 테스트를 작성해야겠다.

특히 테스트 코드를 읽기 쉽도록 Given-When-Then 또는 AAA 패턴을 일관되게 적용하고, 테스트 메서드 이름만으로도 검증하려는 요구사항을 파악할 수 있도록 작성할 예정이다.

이번 수업을 통해 테스트 코드는 단순히 오류를 찾아내는 도구가 아니라, 애플리케이션의 동작을 보장하고 유지보수를 돕는 중요한 코드라는 점을 알게 되었다.

앞으로는 비즈니스 로직을 구현할 때 테스트 가능성을 함께 고려하고, 기능 수정이나 리팩토링 이후에도 기존 동작이 유지되는지 확인해야 겠다.
