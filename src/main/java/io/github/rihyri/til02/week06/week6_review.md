# Week 06 - 학습 및 프로젝트 회고

<br>

6주차에는 트랜잭션의 기본 개념부터 격리 수준, 동시성 문제, Lock을 활용한 데이터 정합성 보장 방법까지 학습했다.

이전까지는 `@Transactional`을 사용하면 여러 DB 작업을 하나로 묶고, 오류 발생 시 롤백할 수 있다는 정도로 이해하고 있었다.

하지만 이번 수업에서는 트랜잭션이 정상적으로 실행되더라도 여러 사용자가 동시에 같은 데이터를 수정하면 예상하지 못한 문제가 발생할 수 있다는 점을 알게 되었다.

특히 단순한 CRUD 기능을 구현하는 것과 실제 서비스에서 데이터의 정합성을 보장하는 것은 서로 다른 문제라는 점이 인상 깊었다.

## 1. 새롭게 이해한 내용

<br>

### 트랜잭션과 데이터 정합성

가장 먼저 트랜잭션을 관리하는 여러 방식을 비교하며 `@Transactional`이 내부적으로 어떤 역할을 수행하는지 이해할 수 있었다.

JDBC에서는 직접 commit과 rollback을 처리해야 하지만, Spring에서는 트랜잭션 관리 기능을 통해 이러한 작업을 자동화할 수 있다는 점을 배웠다.

또한 트랜잭션의 원자성이 보장되더라도 동시성 문제까지 모두 해결되는 것은 아니라는 점을 알게 되었다.

<br>

### 격리 수준과 MVCC

이번 주에 가장 이해하기 어려웠던 내용 중 하나는 트랜잭션 격리 수준이었다.

처음에는 격리 수준을 높이면 모든 동시성 문제가 해결되는 것으로 생각했지만, 실제로는 각 수준에 따라 허용되는 데이터 조회 현상이 다르다는 점을 알게 되었다.

특히 MySQL의 `REPEATABLE READ`에서 다른 트랜잭션이 데이터를 수정하고 커밋하더라도 기존 트랜잭션에서는 이전 값을 조회할 수 있다는 점이 흥미로웠다.

이 과정에서 MVCC가 여러 버전의 데이터를 이용해 일관된 읽기를 지원한다는 것을 이해했다.

<br>

### 비관적 락과 낙관적 락

동시성 문제를 해결하는 방법으로 비관적 락과 낙관적 락을 학습했다.

처음에는 두 방식 모두 데이터 수정을 제한한다는 점에서 비슷하게 느껴졌지만, 학습 후 차이를 구분할 수 있었다.

- 비관적 락은 데이터 수정 전에 충돌을 제어한다.
- 낙관적 락은 데이터를 수정할 때 Version을 이용하여 충돌을 감지한다.

Lock을 적용한다고 무조건 좋은 결과를 얻는 것이 아니라, Lock 대기 시간이나 충돌 빈도까지 고려해야 한다는 점도 배웠다.

## 2. 프로젝트 구현 회고

<br>

이번 프로젝트에서는 기존 상품과 카테고리 기능을 기반으로 쿠폰 발급 및 할인 기능을 구현했다.

쿠폰 조회와 할인 금액 계산도 중요했지만, 가장 신경 써야 했던 부분은 **여러 사용자가 동시에 쿠폰을 발급받거나 등록할 때 데이터의 정합성을 유지하는 것**이었다.

<br>

### 쿠폰 발급 수량의 정합성

쿠폰에 최대 발급 수량이 존재하는 경우, 여러 사용자가 동시에 발급을 요청하면 발급 한도를 초과할 위험이 있다.

단순히 현재 발급 수량을 조회하고 Java 코드에서 한도를 검사한 뒤 저장하는 방식만으로는 동시 요청을 안전하게 처리하기 어렵다는 점을 알게 되었다.

이를 해결하기 위해 발급 가능 여부 조건으로 검사하는 UPDATE 방식을 활용했다.

또한 발급 수량 증가와 사용자 쿠폰 정보 저장을 하나의 트랜잭션으로 묶어, 처리 중 오류가 발생하면 전체 작업이 롤백되도록 구성했다.

이 과정에서 트랜잭션의 원자성과 동시성 제어가 서로 다른 역할을 담당하며, 두 가지를 함께 고려해야 한다는 점을 이해했다.

<br>

## 비관적 락을 이용한 중복 등록 방지

쿠폰을 등록하는 과정에서도 같은 쿠폰이 동시에 등록되는 상황을 고려해야 했다.

이를 위해 `PESSIMISTIC_WRITE`를 이용하여 쿠폰을 조회하고, 쿠폰 상태를 검증한 뒤 변경하는 작업을 하나의 트랜잭션 안에서 처리했다.

특히 단순히 `@Transactional`을 추가하는 것뿐만 아니라, 데이터를 조회하는 시점부터 다른 트랜잭션과의 충돌을 어떻게 제어할 것인지 생각해야 한다는 점을 배웠다.

이번 구현을 통해 수업에서 배운 Lock이 단순한 이론이 아닌 실제 비즈니스 로직의 정합성을 보장하는 데 사용된다는 것을 확인할 수 있었다.

## 마치며 

<br>

이번 6주차는 지금까지 학습한 내용 중에서도 실제 백엔드 개발에서 중요하게 활용할 수 있는 개념들을 배운 시간이었다.

특히 `@Transactional`을 사용하는 방법 자체보다, 어떤 작업을 하나의 트랜잭션으로 묶어야 하는지, 그리고 동시에 실행되는 요청 사이에서 어떤 문제가 발생할 수 있는지를 이해하는 것이 중요하다고 느꼈다.

이번 프로젝트에서 쿠폰 발급과 등록 기능을 구현하며 데이터 정합성을 고려해볼 수 있었다는 점도 의미가 있었다.

아직 격리 수준과 Lock의 세부 동작을 완전히 이해했다고 보기는 어렵지만, 앞으로 기능을 구현할 때 단순히 정상 요청만 고려하는 것이 아니라 **동시 요청과 예외 상황에서도 데이터가 올바르게 유지되는지** 생활하는 습관을 가져야겠다.
