# Week 06 - Day 01. 복습 및 회고

<br>

트랜잭션은 여러 SQL을 단순히 연속 실행하는 것이 아니라 **성공과 실패를 하나의 단위로 관리하는 것**이다. 출금만 성공하고 입금에 실패하는 상황을 이체 예재로 재현하면서 롤백의 필요성을 확인했다.

JDBC에서는 같은 `Connection`을 사용해 `SetAutoCommit(false)` → SQL 실행 → `commit()` 또는 `rollback()`을 직접 수행한다.

Spring의 `PlatformTransactionManager`를 활용하면 연결 처리의 세부사항을 맡기되, 경계는 직접 제어할 수 있다.

`@Transactional`는 트랜잭션 시작과 종료를 Spring 프록시가 처리하므로 비즈니스 코드가 간결해진다.

<br>

### Q1. `save()`나 `update()`가 실행되면 즉시 확정될까?
아니다. SQL이 실행되어도 해당 트랜잭션이 커밋되기 전까지는 취소될 수 있다. SQL의 실행 시점과 영구 반영 시점을 구별해야 한다.

### Q2. `@Transactional`을 붙이면 어떤 예외든 롤백될까?
기본적으로는 `RuntimeException`과 `Error`가 대상이다. 체크 예외도 롤백하려면 `rollbackFor` 등의 설정을 고려해야 한다.

### Q3. Service 내부의 다른 `@Transactional` 메서드를 호출하면 적용될까?
일반적인 Spring 프록시 기반 방시에서는 동일 객체 내부 호출이 프록시를 우회하므로, 호출된 메서드의 별도 트랜잭션 설정이 적용되지 않을 수 있다.

<br>

코드량만 비교하면 `@Transactional`이 단순해 보이지만, 내부적으로 연결과 트랜잭션이 관리된다는 원리를 알아야 롤백 오류를 분석할 수 있다.

이후에는 트랜잭션 내부 호출 문제, 격리 수준 등에 대하여 더 공부를 해야겠다.
