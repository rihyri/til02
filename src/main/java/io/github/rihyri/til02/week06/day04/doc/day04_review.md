# Week 06 - Day 04. 학습 회고

<br>

이번 수업에서는 데이터베이스에서 발생할 수 있는 동시성 문제와 이를 해결하기 위한 Lock을 학습했다.

여러 트랜잭션이 동일한 데이터를 수정할 때 발생하는 `Lost Update` 문제를 알아보고, 비관적 락과 낙관적 락을 이용해 데이터의 정합성을 유지하는 방법을 확인했다.

Spring DATA JPA에서는 `@Lock`과 `@Version`을 통해 이러한 동시성 제어를 구현할 수 있다는 점을 배웠다.

<br>

### Lock과 트랜잭션의 관계

Lock은 단순히 특정 데이터에 접근하지 못하도록 막는 기능이라고 생각했지만, 실제로는 락의 종류에 따라 허용되는 작업이 달라진다는 것을 알게 되었다.

특히 배타적 락을 사용하더라도 InnoDB의 일반적인 SELECT까지 모두 차단되는 것은 아니라는 점이 인상적이었다.

또한 락이 걸리는 범위가 항상 하나의 행으로 고정되는 것은 아니며, 인덱스와 검색 조건에 따라 달라질 수 있다는 점도 알게 되었다.

### 비관적 락과 낙관적 락

비관적 락은 충돌이 발생하기 전에 데이터를 보호하고, 낙관적 락은 데이터가 변경되는 시점에충돌 여부를 검사한다.

비관적 락을 사용하면 다른 트랜잭션이 락을 획득할 때까지 기다릴 수 있지만, 낙관적 락은 버전 충돌이 발생하면 예외가 발생하고 트랜잭션이 롤백될 수 있다.

따라서 단순히 어떤 방식이 더 좋다고 판단하기보다는 서비스의 특성을 고려해야 한다.

<br>

공연 좌석 예약 기능을 구현하면서 동일한 데이터에 여러 요청이 들어오는 상황을 생각해 보았다.

비관적 락에서는 `PESSIMISTIC_WRITE`를 사용하여 데이터를 조회할 때 락을 획득하고, 트랜잭션이 종료되면 락을 해제하는 흐름을 확인했다.

낙관적 락에서는 `@Version`을 사용하여 데이터 수정 시 버전이 일치하는지 검사하는 구조를 학습했다.

또한 `ExecutorService`와 `CountDownLatch`를 사용하면 여러 스레드에서 같은 데이터에 접근하는 상황을 테스트할 수 있다는 점을 알게 되었다.

<br>

이번 학습을 통해 트랜잭션을 사용한다고 해서 모든 동시성 문제가 자동적으로 해결되는 것은 아니라는 점을 이해했다.

데이터베이스의 정합성을 유지하기 위해서는 트랜잭션뿐 아니라 적절한 동시성 제어 전략도 필요하다.

앞으로 예약, 재고 관리, 잔액 변경과 같이 여러 요청이 동일한 데이터에 접근할 수 있는 기능을 구현할 때 락의 필요성을 함께 고려해야겠다.
