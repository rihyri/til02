# Week 09 - Day 01. MSA전환과 Saga 패턴

<br>

이번 수업은 크게 세 부분으로 나뉜다.

1. 하나의 애플리케이션을 여러 서비스로 쪼개면 무엇이 좋아지고 무엇이 어려워지는가 (Monolithic vs MSA)
2. 쪼개진 서비스끼리 어떻게 대화하는가 (메시징 시스템, Kafka, RabbitMQ)
3. DB가 여러 개로 나뉘었을 때 데이터를 어떻게 맞추는가 (최종적 일관성, Saga 패턴)

위 세 부분은 따로 노는 내용이 아니라 하나의 흐름이다.

**서비스를 나누면(1) → 서비스끼리 메시지로 대화해야 하고(2) → 하나의 트랜잭션으로 묶을 수 없으니 메시지를 이용해 데이터를 맞춰야 한다(3).** 

위 흐름을 머릿속에 두고 읽으면 각 개념이 왜 등장하는지 이해가 쉽다.

## 1. Monolithic과 MSA

<br>

### 1.1 Monolithic 아키텍처

회원, 상품, 주문 같은 모든 기능이 **하나의 프로젝트, 하나의 빌드 결과물(jar), 하나의 DB** 안에 들어있는 구조다. 패키지로 기능을 나눠 두었더라도 결국 한 프로세스 안에서 메서드 호출을 서로 부른다.

여기서 헷갈리기 쉬운 점이 있다. 모놀리틱이라고 서버가 반드시 1대인 것은 아니다. 같은 jar를 서버 여러 대에 똑같이 띄울 수 있다. **애플리케이션의 종류가 하나**라는 뜻이지 **서버 대수가 하나**라는 뜻은 아니다.

- **장점 :** 구조가 단순해서 초기 개발과 배포가 빠르다. 디버깅과 테스트가 쉽다. 하나의 DB 트랜잭션으로 여러 테이블 작업을 한 번에 묶을 수 있다.
- **단점 :** 일부 기능만 바빠도 전체를 늘려야 한다. 작은 수정에도 전체를 다시 배포해야 한다. 시간이 지날수록 코드끼리 얽혀서 고치기 어려워진다.

<br>

### 1.2 MSA (Microservices Architecture)

애플리케이션을 **비즈니스 기능 단위로 나누어, 각각 독립적으로 배포하고 실행하는 작은 서비스들의 모음**으로 만드는 구조다.

같은 쇼핑몰이라면 user 서비스, product 서비스, order 서비스가 각각 다른 포트에서 따로 실행되고, **DB도 각자 가진다.** 그래서 주문 서비스는 더 이상 상품 테이블을 직접 조회할 수 없다. 상품 정보가 필요하면 네트워크(HTTP 호출이나 메시지)를 통해 상품 서비스에 물어봐야 한다.

- **독립 배포 :** 서비스마다 따로 빌드하고 배포한다.
- **폴리글랏(Polyglot) :** 서비스 성격에 맞춰 언어, 프레임워크, DB를 다르게 고를 수 있다. 예를 들어 검색은 검색 엔진, 추천은 Python을 쓸 수 있다.
- **네트워크 기반 통신 :** 서비스 사이의 호출은 HTTP/REST, gRPC 같은 동기 호출이나 Kafka, RabbitMQ 같은 메시지 브로커를 이용한 비동기 통신으로 이루어진다.

### 1.3 세 가지 관점으로 비교하기

#### · 확장성 (Scalability)

트래픽이 늘었을 때 얼마나 효율적으로 버틸 수 있는지에 대한 관점이다.

        </tr>

</table>

<br>

#### · 유지보수성 (Maintainability)

버그를 고치거나 기능을 추가할 때 얼마나 안전하고 빠르게 바꿀 수 있는지에 대한 관점이다.

- **모놀리틱 :** 코드가 한 곳에 모여 있어서 서로 얽히기 쉽다. A 기능을 고쳤는데 관련 없어 보이는 B 기능이 깨지는 일이 생긴다.
- **MSA :** 서비스마다 범위가 작고 목적이 분명하다. 서비스 사이의 약속(API 스펙, 메시지 형식)만 지키면 내부 구현을 바꿔도 다른 서비스에 영향이 없다. 이것을 **느슨한 결합 (Loose Coupling)** 이라고 한다.

<br>

#### · 복잡성 (Complexity) ⭐

이 부분이 핵심이다. **두 구조 모두 결국 복잡해진다. 다만 복잡함이 찾아오는 시점이 다르다.**

    <thead>
        <th>시점</th>
        <th>모놀리틱</th>
        <th>MSA</th>
    </thead>
    <tbody>
        <tr>
            <td>초기</td>
            <td>낮음 (프로젝트 하나만 신경 쓰면 됨)</td>

        </tr>
        <tr>
            <td>성장 후</td>
            <td>계속 높아짐 (코드가 서로 얽힘)</td>

        </tr>
    </tbody>

- `모놀리틱 = 처음엔 쉽고 나중에 어렵다.` 시작할 때는 프로젝트 하나만 신경 쓰면 된다. 하지만 기능이 쌓일수록 내부가 엉킨다.
- `MSA = 처음부터 어렵고 이후 안정된다.` 시작 단계부터 서비스 간 통신 방식, 분산 데이터 설계, 서비스별 배포 파이프라인을 다 갖춰야 한다. 운영 중에는 요청 하나가 여러 서비스를 거치므로 어디서 느려지고 어디서 실패했는지 찾기 어렵다. 그래서 로그 수집과 분산 추적 같은 도구가 사실상 필수다.

<br>

**그래서 작은 서비스나 초기 스타트업에 MSA부터 도입하는 것은 오히려 손해일 수 있다.**

## 2. MSA를 도입하기 전에 갖춰야 할 것

<br>

MSA는 코드 구조만 바꾼다고 되는 것은 아니다. 조직, 데이터, 인프라가 같이 준비되어야 한다.

<br>

### 2.1 조직과 문화
- **CI/CD 자동화 :** 서비스가 수십 개로 늘어나면 사람이 손으로 빌드하고 배포하는 것이 불가능하다. 커밋하면 테스트와 배포가 자동으로 이루어져야 한다.
- **교차 기능 팀 :** 한 서비스를 기획부터 운영까지 한 팀이 책임질 수 있는 구조가 필요하다. 서비스는 나눴는데 의사결정은 여전히 한 곳에서 한다면 MSA의 장점이 사라진다.

<br>

### 2.2 서비스 경계 정하기 (Bounded Context)

MSA에서 가장 어려운 질문은 **어디를 기준으로 자를 것인가**다.

- 도메인 주도 설계(DDD)의 **Bounded Context**를 기준으로 삼는다. 같은 단어라도 맥락에 따라 의미가 달라지는 지점이 경계가 된다. 예를 들어 "상품"은 전시 맥락에서는 이미지와 설명이 중요하고, 재고 맥락에서는 수량이 중요하다.
- 경계를 잘못 나누면 **분산 모놀리스 (Distributed Monolith)** 가 된다. 기능 하나를 바꿀 때마다 여러 서비스를 동시에 고치고 동시에 배포해야 하는 상태다. 모놀리틱의 단점은 그대로인데 네트워크 비용만 추가된, 가장 나쁜 형태다.

<br>

### 2.3 데이터 분리와 일관성

- **Database per Service :** 각 서비스는 자기 DB만 사용한다. 다른 서비스의 테이블을 직접 JOIN하거나 조회하면 안 된다.
- **2PC (Two-Phase Commit)의 한계 :** 여러 DB를 하나의 트랜잭션으로 묶는 전통적인 방법이다. 모든 참여자가 "준비 완료"라고 답할 때까지 잠금을 유지하므로 느리고, 이를 조율하는 코디네이터가 멈추면 전체가 멈춘다.
- 그래서 MSA에서는 **비동기 메시지로 시간이 지나면 결국 데이터를 맞추는 방식(Saga 패턴)** 을 주로 쓴다.

<br>

### 2.4 관찰 가능성 (Observability)

- **분산 추적 :** 요청 하나가 5-6개 서비스를 지나갈 때, 어느 구간이 느렸고 어디서 실패했는지 하나의 흐름으로 볼 수 있어야 한다.
- **중앙 로그 수집과 메트릭 :** 서버마다 접속해서 로그를 볼 수 없다. 모든 서비스의 로그와 지표를 한 곳에 모아보고 시각화해야 한다.

<br>

### 2.5 네트워크 통신

메서드 호출이 네트워크 호출로 바뀌면서 새로 생기는 문제들이다.

- **서비스 디스커버리 :** 컨테이너가 환경에서는 인스턴스가 수시로 생기고 사라져서 IP가 계속 바뀐다. 그래서 각 서비스가 자기 위치를 레지스트리에 등록하고, 호출하는 쪽은 IP 대신 **서비스 이름**으로 찾아간다. (예: Spring Cloud Netflix Eureka)
- **API 게이트웨이 :** 외부 요청이 들어오는 단일 입구다. 요청을 알맞은 서비스로 넘겨주고, 인증, 로깅, 요청량 제한 같은 공통 작업을 한 곳에 처리한다.
- **장애 전파 차단 :** 서비스 하나가 느려지거나 죽었을 때 이를 호출하던 다른 서비스들까지 응답을 기다리다 줄줄이 멈추는 것을 막아야 한다. (타임아웃, 서킷 브레이커 등)

<br>

### 2.6 보안

- **외부 → 내부 :** API 게이트웨이에서 JWT나 OAuth 2.0으로 인증/인가를 한 번에 처리한다.
- **내부 ↔ 내부 :** "내부망이니까 안전하다"고 가정하지 않는다. 서비스끼리도 서로를 인증하는 **제로 트러스트** 모델을 고려한다.

## 3. 실패하지 않는 MSA 전환 전략

<br>

### 3.1 한 번에 갈아엎지 않는다. (Strangler Fig 패턴)

Stranger Fig(교살자 무화가)는 숙주 나무를 감싸며 자라다가 결국 숙주를 대체하는 덩굴 식물이다.

이름처럼 **기존 모놀리틱을 그대로 운영하면서 기능을 하나씩 새 서비스로 옮기고, 앞단의 라우팅 (API 게이트웨이 등)을 조금씩 새 서비스 쪽으로 돌린다.** 마지막에 기존 시스템에 남은 기능이 없으면 걷어낸다.

```aiignore
[1단계]  요청 ──> 게이트웨이 ──> 모놀리틱(회원, 상품, 주문)

[2단계]  요청 ──> 게이트웨이 ──┬──> 모놀리틱(회원, 상품)
                              └──> 주문 서비스 (새로 분리)

[3단계]  요청 ──> 게이트웨이 ──┬──> 회원 서비스
                              ├──> 상품 서비스
                              └──> 주문 서비스      (모놀리틱 제거)
```

Microsoft Azure 아키텍처 문서에서도 이 패턴을 레거시 시스템을 점진적으로 마이그레이션하는 방법으로 소개한다. 한 번에 바꾸는 "빅뱅" 전환보다 위험이 적고, 문제가 생기면 라우팅만 되돌리면 된다.

<br>

### 3.2 가치가 큰 것부터 떼어낸다.

모든 기능을 쪼갤 필요는 없다. **트래픽 변동이 큰 기능, 배포가 잦은 기능**처럼 분리했을 때 얻는 이익(ROI)이 큰 것부터 옮긴다.

<br>

### 3.3 자동화가 먼저다.

CI/CD, 인프라를 코드로 관리하는 **IaC(Infrastructure as Code),** 통합 모니터링이 갖춰져 있어야 늘어난 서비스 수를 감당할 수 있다.

## 4. 메시징 시스템

<br>

### 4.1 왜 메시징이 필요한가

서비스를 나누면 서로 대화할 방법이 필요하다. 가장 단순한 방법은 HTTP로 직접 호출하는 것이다. 하지만 직접 호출은 **상대가 지금 살아 있어야 하고, 내가 누구를 불러야 하는지 알아야 한다.**

메시징 시스템은 서비스 사이에 **중간 보관소**를 둔다. 보내는 쪽은 보관소에 메시지를 넣고 자기 할 일을 계속한다. 받는 쪽은 자기 속도에 맞춰 보관소에서 메시지를 꺼내 처리한다.

```aiignore
[직접 호출]    주문 서비스 ──HTTP──> 재고 서비스     (재고 서비스가 죽으면 주문도 실패)

[메시징]       주문 서비스 ──> [ 브로커 ] ──> 재고 서비스
                                        └──> 통계 서비스
                                        └──> 알림 서비스
               (주문 서비스는 누가 받아 가는지 몰라도 된다)
```

### 4.2 명령이 아니라 "사실"을 알린다. (이벤트 설계)

메시지를 설계할 때 가장 중요한 감각이다.

<table>
    <thead>

이벤트를 만들 때 지켜야 할 두 가지 규칙이 있다.

1. **받는 대상을 지정하지 않는다. :** "재고 서비스에게"라는 말이 들어가면 안 된다.
2. **기대하는 효과를 말하지 않는다. :** "재고를 줄여줘"가 아니라 **"나는 ~했다."** 라는 과거형 사실만 말한다.

이렇게 말하면 나중에 알림 서비스나 통계 서비스가 추가되어도 주문 서비스는 코드를 고칠 필요가 없다.

새 서비스가 "주문 생성됨" 이벤트를 구독하기만 하면 된다. 이벤트 이름도 `OrderCreated`, `PaymentCompleted`처럼 과거형으로 짓는 경우가 많다.

## 5. Apache Kafka 처음부터 이해하기

<br>

### 5.1 Kafka를 한 문장으로

Kafka 공식 문서는 파티션을 **계속해서 뒤에 덧붙여지는, 순서가 있고 변경할 수 없는 레코드의 나열 = 구조화된 커밋 로그**라고 설명한다.

쉽게 말하면 Kafka는 **절대 지우지 않고 뒤에만 계속 적는 장부**다. 일반적인 메시지 큐는 누군가 메시지를 꺼내 가면 그 메시지가 사라진다. Kafka는 메시지를 읽어 가도 지우지 않는다. 정해진 보관 기간(retention)이 지날 때까지 디스크에 그대로 남아 있다. 그래서 여러 서비스가 같은 메시지를 각자 읽을 수 있고, 필요하면 과거 메시지를 다시 읽을 수 있다.

<br>

### 5.2 비유로 먼저 이해하기 : 회사 공지 게시판

용어가 한꺼번에 나와서 어렵게 느껴지므로, 먼저 하나의 그림으로 이해하고 그 다음 용어를 하나씩 대응시킨다.

> 어느 회사에 **주문 게시판**이 있다. 글이 너무 많이 올라와서 **노트 3권**으로 나눠 쓴다. 새 글은 각 노트의 **맨 아래 줄에만** 적을 수 있고, 이미 적힌 글들은 고칠 수 없다. 각 줄에는 **줄 번호**가 붙는다.
> 
> 같은 주문번호에 대한 글은 **항상 같은 노트**에 적는다는 규칙이 있다. 그래서 한 주문의 "생성 → 결제 → 배송" 글은 한 노트 안에서 순서대로 쌓인다.
> 
> 이 게시판을 읽는 팀은 여럿 있다. **재고팀**은 팀원 3명이 노트를 한 권씩 나눠 맡아 읽는다. **통계팀**도 같은 노트를 자기들끼리 따로 읽는다. 재고팀이 읽었다고 글이 지워지지 않으므로 통계팀도 똑같은 글을 볼 수 있다.
> 
> 각 팀은 노트마다 **어디까지 읽었는지 책갈피**를 꽂아 둔다. 팀원이 퇴근했다가 돌아오면 책갈피 위치부터 다시 읽는다. 팀원 한 명이 결근하면, 그 사람이 맡던 노트를 다른 팀원이 **넘겨받는다.**
> 
> 노트는 **보관 창고(서버) 여러 곳**에 복사본을 둔다. 창고 하나에 불이 나도 다른 창고의 복사본으로 계속 운영한다.

### 5.4 용어 하나씩 자세히

#### · 브로커와 클러스터

브로커는 Kafka 서버 프로그램 하나를 말한다. 브로커는 메시지를 **보관만** 한다. 메시지를 컨슈머에게 밀어 넣지 않고, **컨슈머가 직접 와서 가져간다(pull 방식).** 그래서 컨슈머는 자기가 처리할 수 있는 속도만큼 가져갈 수 있다.

예전 Kafka는 클러스터 정보를 확인하기 위해 ZooKeeper라는 별도 시스템이 필요했다. 지금은 Kafka 자체가 이 역할을 하는 **KRaft 모드**를 사용하고, Kafka 4.0부터는 Zookeeper 없이 KRaft로만 동작한다.

#### · 토픽과 파티션

토픽은 "어떤 종류의 메시지인가"를 나타내는 이름이다. 이커머스라면 `order-event`, `payment-event`처럼 도메인의 행동 단위로 만든다.

토픽 하나를 여러 파티션으로 나누는 이유는 **처리량** 때문이다. 장부가 1권이면 한 명만 읽을 수 있지만, 3권으로 나누면 3명이 동시에 읽을 수 있다.

```aiignore
토픽: order-event

파티션 0 : [0][1][2][3][4][5] ← 새 메시지는 항상 맨 뒤에 추가
파티션 1 : [0][1][2][3]
파티션 2 : [0][1][2][3][4]
            ↑
          오프셋 (파티션마다 0부터 따로 센다)
```

#### · 메시지 키와 순서 보장

프로듀서가 메시지에 키를 붙이면, Kafka는 **키의 해시값을 파티션 수로 나눈 나머지**로 파티션을 고른다. (`hash(key) % 파티션 수`) 그래서 **같은 키는 항상 같은 파티션**으로 간다.

이것이 중요한 이유는 **Kafka가 순서를 보장하는 범위가 "파티션 안"뿐이기 때문**이다. 공식 문서에서도 "Kafka는 파티션 안에서만 전체 순서를 보장하고, 토픽의 서로 다른 파티션 사이에서는 보장하지 않는다."고 명시한다.

**순서가 중요한 메시지는 반드시 같은 키(예: 주문ID)를 붙여서 보내야 한다.**

```aiignore
주문 1001번의 이벤트 : 생성 → 결제 → 배송
  키 = "1001" 로 보내면  → 모두 같은 파티션 → 순서대로 처리된다 ✅
  키 없이 보내면         → 여러 파티션으로 흩어질 수 있음 → 결제가 생성보다 먼저 처리될 수도 있다 ❌
```

#### · 컨슈머 그룹

컨슈머 그룹을 이해할 때 아래 두 문장만 기억하면 된다.

1. **같은 그룹 안에서는 나눠 읽는다.** 한 파티션은 그룹 안에서 딱 한 컨슈머만 담당한다.
2. **다른 그룹끼리는 전부 각자 읽는다.** 공식 문서 표현으로는 "토픽에 발행된 각 레코드는 구독 중인 각 컨슈머 그룹 안의 하나의 컨슈머 인스턴스에게 전달된다."

```aiignore
토픽 order-event (파티션 3개)

[재고 그룹]                          [통계 그룹]
  컨슈머 A ← 파티션 0                   컨슈머 X ← 파티션 0, 1, 2 전부
  컨슈머 B ← 파티션 1
  컨슈머 C ← 파티션 2

→ 재고 그룹은 3명이 나눠서, 통계 그룹은 1명이 전부. 두 그룹 모든 메시지를 각자 받는다.
```

그래서 **파티션 수가 한 그룹의 최대 병렬 처리 수**가 된다. 파티션이 3개인데 컨슈머를 5개 띄우면 2개는 맡을 파티션이 없어서 **놀게 된다.** 처리량을 늘리고 싶으면 컨슈머만 늘릴 것이 아니라 파티션 수도 함께 고려해야 한다.

#### · 리밸런싱

그룹 안의 구성원이 바뀌면(컨슈머가 죽거나, 새로 추가되거나) 파티션 담당을 다시 나누는 과정이다.

```aiignore
[평소]          A ← P0      B ← P1      C ← P2
[B가 죽음]      A ← P0, P1  C ← P2           (B가 맡던 P1을 A가 넘겨받음)
```

#### · 오프셋 커밋

컨슈머 그룹은 파티션마다 **여기까지 처리했다**는 위치를 Kafka에 기록한다. 이것이 오프셋 커밋이다. 컨슈머가 재시작하거나 리밸런싱으로 다른 컨슈머가 파티션을 넘겨받으면, **마지막으로 커밋된 위치부터** 다시 읽는다.

여기서 하나 알아둘 점이 있다. 메시지를 처리한 뒤 커밋하기 직전에 컨슈머가 죽으면, 재시작했을 때 그 메시지를 **한번 더** 읽게 된다. 그래서 컨슈머는 **같은 메시지를 두 번 받아도 결과가 달라지지 않도록 (멱등성)** 만드는 것이 좋다. 예를 들어 처리한 이벤트 ID를 저장해두고 이미 처리한 ID면 건너뛰는 식이다.

#### · 복제 (Replication)

수업에서는 "브로커를 3대 이상 둔다"고만 나왔는데, 그 이유가 복제다. 공식 문서에 따르면 각 파티션은 **리더(leader) 1개와 팔로워(follower) 0개 이상**을 가진다. 읽기와 쓰기는 리더가 처리하고, 팔로워는 리더의 데이터를 복사해 둔다. 리더가 있는 브로커가 죽으면 팔로워 중 하나가 새 리더가 된다. 그래서 브로커 한 대가 죽어도 메시지가 유실되지 않는다.

<br>

## 6. RabbitMQ와 비교하기

<br>

### 6.1 RabbitMQ는 "우체국"이다

kafka가 "지워지지 않는 장부"라면 RabbitMQ는 **배달이 끝나면 사라지는 우체국**이다.

RabbitMQ는 AMQP 0-9-1 프로토콜을 따르는 전통적인 메시지 브로커다.

```aiignore
프로듀서 ──> [Exchange] ──바인딩 규칙──> [Queue] ──> 컨슈머 ──ACK──> 큐에서 삭제
              (우체부)                  (우편함)
```

- **Exchange :** 프로듀서가 보낸 메시지를 받아서 어느 큐로 보낼지 결정하는 라우터다. 프로듀서는 큐에 직접 넣지 않고 Exchange에 보낸다.
- **Binding :** Exchange와 Queue를 잇는 배달 규칙이다.
- **Queue :** 메시지가 실제로 쌓이는 곳이다.
- **ACK :** 컨슈머가 "처리 완료"라고 알려주면 브로커가 메시지를 삭제한다. ACK 없이 컨슈머가 죽으면 다른 컨슈머에게 다시 전달한다. 

<br>

### 6.2 Exchange 종류

RabbitMQ 공식 문서는 네 가지 Exchange 타입을 소개한다.

<table>
    <thead>
        <th>타입</th>
        <th>배달 방식</th>
        <th>비유</th>
    </thead>
    <tbody>
        <tr>
            <td>Direct</td>
            <td>라우팅 키가 정확히 일치하는 큐로</td>
            <td>정확한 주소로 배달</td>
        </tr>
        <tr>
            <td>Fanout</td>
            <td>라우팅 키를 무시하고 연결된 모든 큐로</td>
            <td>전체 공지</td>
        </tr>
        <tr>
            <td>Topic</td>
            <td>라우팅 키를 패턴(order.* 등)으로 매칭</td>
            <td>지역별 배달</td>
        </tr>
        <tr>
            <td>Headers</td>
            <td>라우팅 키 대신 메시지 헤더 값으로 매칭</td>
            <td>조건별 분류</td>
        </tr>
    </tbody>
</table>

그 밖에 메시지별 ACK/NACK, 재전달, 우선순위 큐, 처리에 실패한 메시지를 따로 모으는 **DLX(Dead Letter Exchange)** 같은 세밀한 제어 기능이 강점이다.

## 7. 분산 환경에서 데이터 일관성 맞추기 ⭐⭐⭐

<br>

이번 수업에서 가장 중요한 부분이다.

<br>

### 7.1 모놀리틱에서는 왜 쉬웠나

모놀리틱에서는 주문 생성, 사용자 확인, 재고 차감이 **하나의 DB 트랜잭션** 안에서 일어난다. 중간에 재고가 부족해서 예외가 나면, 앞에서 이미 차감한 재고까지 **DB가 알아서 전부 되돌린다(롤백).** 개발자는 `@Transactional` 하나만 붙이면 된다. 이것이 ACID 트랜잭션이다.

<table>
    <thead>
        <th>ACID</th>
        <th>의미</th>
    </thead>
    <tbody>
        <tr>
            <td>Atomicity (원자성)</td>
            <td>전부 성공하거나 전부 실패한다.</td>
        </tr>
        <tr>
            <td>Consistency (일관성)</td>
            <td>트랜잭션 전후로 데이터가 규칙에 맞는 상태를 유지한다.</td>
        </tr>
        <tr>
            <td>Isolation (격리성)</td>
            <td>동시에 실행되는 트랜잭션끼리 서로 간섭하지 않는다.</td>
        </tr>
        <tr>
            <td>Durability (지속성)</td>
            <td>커밋된 결과는 장애가 나도 남는다.</td>
        </tr>
    </tbody>
</table>

<br>

### 7.2 MSA에서는 왜 어려운가

MSA에서는 주문 DB, 사용자 DB, 상품 DB가 **물리적으로 다르다.** 주문 서비스의 `@Transactional`
은 주문 DB만 롤백할 수 있다. 상품 서비스가 이미 커밋한 재고 차감을 주문 서비스가 되돌릴 방법이 없다. 

2PC로 묶을 수 있지만, 앞에서 본 것처럼 잠금 시간이 길고 코디네이터 장애에 약해서 MSA에서는 잘 쓰지 않는다.

<br>

### 7.3 최종적 일관성 (Eventual Consistency)

그래서 MSA는 발상을 바꾼다. **"모든 DB가 매 순간 일치해야 한다"는 목표를 포기하고, "잠깐 어긋나도 결국에 맞춰진다"를 받아들인다.** 이것이 최종적 일관성이다.

```aiignore
시간   주문 DB            상품 DB          상태
T0    (없음)              재고 10          주문 요청 들어옴
T1    주문 = PENDING      재고 10          ← 주문은 있는데 재고는 그대로 (불일치)
T2    주문 = PENDING      재고 8           ← 재고는 줄었는데 주문은 아직 대기 (불일치)
T3    주문 = COMPLETED    재고 8           ← 드디어 일치
```
**T1 ~ T2 사이에는 두 DB가 서로 다른 이야기를 한다.** 이 어긋남을 사용자에게 그대로 보여주면 안 되므로, 주문 API는 처음에 **"주문이 접수되었습니다(PENDING)"** 라고 먼저 응답한다. 이후 화면에서 상태를 다시 조회하여 최종 결과("주문 완료" 또는 "주문 취소")를 보여준다.
배달 앱에서 "주문 접수 중..."이 잠깐 뜨다가 "주문 완료"로 바뀌는 것과 같다.

<br>

### 7.4 Saga 패턴

Saga는 최종적 일관성을 애플리케이션 코드로 구현하는 대표적인 방법이다. Microsoft 아키텍처 문서의 정의를 정리하면 다음과 같다.

- 하나의 큰 분산 트랜잭션을 **여러 개의 로컬 트랜잭션의 연속**으로 쪼갠다.
- 각 로컬 트랜잭션은 **자기 서비스의 DB만** 변경하고 커밋한다.
- 커밋이 끝나면 **이벤트나 메시지를 발행해 다음 단계를 시작**시킨다.
- 중간 단계가 실패하면, 앞에서 이미 성공한 단계들을 **보상 트랜잭션(Compensating Transaction)** 으로 되돌린다.

#### · 보상 트랜잭션이란?

**롤백이 아니라 "반대 작업"을 새로 실행하는 것**이다. 이미 커밋된 데이터는 DB 차원에서 되돌릴 수 없으므로, 반대 효과를 내는 새 트랜잭션을 실행한다.

<table>
    <thead>
        <th>원래 작업</th>
        <th>보상 작업</th>
    </thead>
    <tbody>
        <tr>
            <td>주문 생성 (PENDING)</td>
            <td>주문 상태를 CANCELED로 변경</td>
        </tr>
        <tr>
            <td>재고 2개 차감</td>
            <td>재고 2개 다시 증가</td>
        </tr>
        <tr>
            <td>결제 승인</td>
            <td>결제 취소 (환불)</td>
        </tr>   
        <tr>
            <td>포인트 사용</td>
            <td>포인트 복구</td>
        </tr>
    </tbody>
</table>

보상 트랜잭션은 데이터를 지우는 것이 아니라 **기록을 남기면서 상태를 바꾸는 것**이다. 주문을 삭제하지 않고 CANCELED로 바꾸는 이유가 이거다. 은행에서 잘못 송금했을 때 기록을 지우지 않고 반대 거래를 하나 더 남기는 것과 같다.

<table>
    <thead>
        <th>단계</th>
        <th>담당 서비스</th>
        <th>하는 일</th>
        <th>실패하면?</th>
    </thead>
    <tbody>
        <tr>
            <td>T1</td>
            <td>주문 서비스</td>
            <td>주문을 PENDING 상태로 저장</td>
            <td>-</td>
        </tr>
        <tr>
            <td>T2</td>
            <td>사용자 서비스</td>
            <td>주문한 사용자가 유효한지 검증</td>
            <td>C1 실행</td>
        </tr>
        <tr>
            <td>T3</td>
            <td>상품 서비스</td>
            <td>재고 차감</td>
            <td>C1 실행</td>
        </tr>
        <tr>
            <td>C1</td>
            <td>주문 서비스</td>
            <td>주문 상태를 CANCELLED로 변경 (보상)</td>
            <td>-</td>
        </tr>
    </tbody>
</table>

<br>

#### · 성공하는 경우

```aiignore
T1 주문 생성(PENDING) ──> T2 사용자 검증 OK ──> T3 재고 차감 OK ──> 주문 COMPLETED
```

#### · T2에서 실패하는 경우 (존재하지 않는 사용자)

```aiignore
T1 주문 생성(PENDING) ──> T2 사용자 검증 실패 ❌
                                   │
         C1 주문 CANCELLED  <──────┘  (되돌릴 것은 T1뿐)
```

#### · T3에서 실패하는 경우 (재고 부족)
```aiignore
T1 주문 생성(PENDING) ──> T2 사용자 검증 OK ──> T3 재고 차감 실패 ❌
                                                        │
         C1 주문 CANCELLED  <───────────────────────────┘
```

- **T2(사용자 검증)는 아무 데이터도 바꾸지 않는다.** 조회만 하므로 되돌릴 것이 없다.
- **T3(재고 차감)가 실패했다는 것은 상품 서비스의 로컬 트랜잭션이 롤백되었다는 뜻이다.** 재고는 처음부터 줄어들지 않았으니 되돌릴 것이 없다.
- **결국 실제로 커밋되어 남아 있는 변경은 T1(주문 생성)뿐이다.** 그래서 보상도 C1 하나면 충분하다.

만약 T3 뒤에 T4(결제)가 있고 T4가 실패했다면, 이번에는 T3에서 이미 커밋된 재고 차감을 되돌리는 **C3(재고 복구)** 도 필요하다. 보상은 **성공한 단계를 역순으로** 되돌린다.

```aiignore
T1 ──> T2 ──> T3 ──> T4 실패 ❌
C1 <── (C2 없음) <── C3 <──┘
```

<br>

### 7.5 공식 문서에서 추가로 알아둘 것

#### · 트렌잭션의 세 종류 

Microsoft 문서는 Saga 안의 트랜잭션을 세 가지로 구분한다.

- **보상 가능 트랜잭션 (Compensable) :** 반대 작업으로 되돌릴 수 있는 단계 (예: 주문 생성, 재고 차감)
- **피벗 트랜잭션 (Pivot) :** 되돌릴 수 없는 지점. 이 단계가 성공하면 Saga는 끝까지 가야 한다. (예: 실제 출고)
- **재시도 가능 트랜잭션 (Retryable) :** 피벗 이후의 단계. 멱등하게 만들어 일시적인 실패가 나도 재시도해서 결국 성공시킨다. (예: 알림 발송)

<br>

#### · Saga에는 격리성(Isolation)이 없다.

하나의 DB 트랜잭션은 끝나기 전까지 중간 상태를 다른 트랜잭션에게 보여주지 않는다. Saga는 각 단계가 바로 커밋되므로 **중간 상태가 다른 요청에 그대로 보인다.** 예를 들어 T3에서 재고를 차감했지만 이후 단계에서 실패해 곧 복구될 재고를 다른 주문이 읽어갈 수 있다.

Microsoft 문서는 이런 문제(lost update, dirty read 등)를 줄이는 방법으로 **Semantic Lock**을 소개한다. 처리 중인 데이터에 "처리 중"이라는 표시를 해두는 방식이다. **주문의 PENDING 상태가 바로 이 역할을 한다.** PENDING인 주문은 아직 확정된 것은 아니므로 다른 로직이 이를 근거로 무엇을 하면 안 된다는 표시이다.

<br>

#### · DB 저장과 메시지 발행을 함께 성공시키는 문제 

Saga의 각 단계는 "내 DB 커밋"과 "다음 단계를 위한 이벤트 발행"을 둘 다 해야한다. 그런데 DB 커밋은 성공했는데 Kafka 발행이 실패하면, 주문은 생겼는데 다음 단계가 영영 시작되지 않는다.

microservices.io(Saga 패턴을 정리한 Chris Richardson의 사이트)는 이를 해결하는 방법으로 **Transactional Outbox 패턴**을 소개한다. 이벤트를 바로 브로커에 보내지 않고 **같은 DB 트랜잭션 안에서 outbox 테이블에 함께 저장**한 뒤, 별도 프로세스가 outbox 테이블을 읽어 브로커로 발행하는 방식이다. 이번 수업 범위는 아니지만 Saga를 실제로 구현할 때 반드시 마주치는 문제라 같이 기록해둔다.

## 8. Saga 구현 방식 : Choreography vs Orchestration

<br>

### 8.1 Choreography (안무형)

**중앙 지휘자 없이, 각 서비스가 이벤트를 듣고 스스로 다음 행동을 결정**하는 방식이다. 무용수들이 지휘자 없이 음악(이벤트)에 맞춰 각자 정해진 동작을 하는 것과 같다.

```aiignore
주문 서비스 ──"주문 생성됨"──> [Kafka]
                                 │
사용자 서비스 <──────────────────┘ (구독)
사용자 서비스 ──"사용자 검증됨"──> [Kafka]
                                   │
상품 서비스 <──────────────────────┘ (구독)
상품 서비스 ──"재고 차감됨" 또는 "재고 차감 실패"──> [Kafka]
                                                     │
주문 서비스 <────────────────────────────────────────┘ (구독) → COMPLETED 또는 CANCELLED
```

주문 서비스는 "주문이 생성됐다"는 사실만 알린다. 다음 단계를 누가 하는지는 **누가 어떤 이벤트를 구독하느냐**로 결정된다. 4장의 이벤트 설계 규칙(대상 지정 X, 기대 효과 X)이 그대로 적용되는 방식이다.

- **장점 :** 서비스끼리 서로를 모르므로 결합도가 낮다. 별도의 조정 서비스가 필요 없다. 단일 장애 지점이 없다.
- **단점 :** 전체 흐름이 코드 한곳에 없고 여러 서비스에 흩어져 있어서 파악하기 어렵다. 단계가 늘어 날수록 서비스끼리 서로의 이벤트를 구독하다가 **순환 의존**이 생길 수 있다. 통합 테스트를 하려면 모든 서비스를 다 띄어야 한다.

<br>

### 8.2 Orchestration (지휘형)

**중앙의 오케스트레이터가 각 서비스에 순서대로 "명령"을 보내고, 결과를 받아서 다음 단계를 결정**하는 방식이다. 오케스트라 지휘자가 각 파트에 언제 연주할지 지시하는 것과 같다.

```aiignore
                  ┌──"사용자 검증해"──> 사용자 서비스
                  │<──── 결과 ───────┘
오케스트레이터 ───┤
(주문 Saga)       ├──"재고 차감해"────> 상품 서비스
                  │<──── 결과 ───────┘
                  │
                  └── 실패 시 "주문 취소해" ──> 주문 서비스
```

Choreography와 가장 큰 차이는 **오가는 것이 이벤트(사실)가 아니라 명령(지시)** 이라는 점이다.

- **장점 :** 전체 흐름이 오케스트레이터 한 곳에 모여 있어 이해하기 쉽다. 복잡한 분기나 보상 흐름을 제어하기 좋다. 서비스끼리 서로를 구독하지 않으므로 순환 의존이 생기지 않는다.
- **단점 :** 오케스트레이터에 조정 로직을 따로 구현해야 한다. 비즈니스 로직이 오케스트레이터로 몰릴 수 있다. 오케스트레이터가 멈추면 전체 흐름을 멈추는 **단일 장애 지점**이 된다.

## 9. 핵심 정리

- **모놀리틱은 처음에 쉽고 나중엔 어렵고, MSA는 처음부터 어렵지만 이후 안정된다.** 무조건 MSA가 좋은 것은 아니다.
- MSA 전환은 **Strangler Fig 패턴**으로 한 기능씩 점진적으로 옮긴다. 경계를 잘못 나누면 **분산 모놀리스**가 된다.
- 메시징 시스템은 서비스 사이에 중간 보관소를 두어 결합도를 낮춘다. 이벤트는 **대상과 기대 효과 없이 "~했다"는 사실**만 담는다.
- **Kafka는 읽어도 지우지 않는 장부**다. 토픽은 파티션으로 나뉘고, 순서는 **파티션 안에서만** 보장된다. 순서가 필요하면 **같은 키**로 보낸다.
- **같은 컨슈머 그룹은 나눠 읽고, 다른 그룹은 각자 전부 읽는다.** 파티션 수가 그룹의 최대 병렬도다.
- **RabbitMQ는 배달 후 사라지는 우체국**이다. Exchange 타입에 따라 유연한 라우팅이 강점이다.
- MSA에서는 DB가 나뉘어 ACID 트랜잭션을 쓸 수 없으므로 **최종적 일관성**을 받아들인다.
- **Saga = 로컬 트랜잭션의 연속 + 실패 시 보상 트랜잭션.** 보상은 롤백이 아니라 **반대 작업**이며, **성공한 단계만 역순으로** 되돌린다.
- Saga 구현은 **이벤트로 각자 움직이는 Choreography**와 **중앙에서 명령하는 Orchestration** 두 가지가 있다.
