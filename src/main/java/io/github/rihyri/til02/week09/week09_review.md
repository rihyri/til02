# Week 09 - 학습 및 프로젝트 회고

<br>

9주차에는 MSA 전환과 Saga 패턴, DDD, Kafka 이벤트 시스템 설계, 그리고 분산 추적과 메트리그 모니터링에 대해 학습했다.

8주차까지는 하나의 애플리케이션 안에서 기능을 구현하고, 코드의 구조와 테스트, 보안을 개선하는데 집중했다.

하지만 이번 주에는 애플리케이션이 여러 서비스로 나뉘면서 하나의 트랜잭션으로 해결하던 문제들을 더 이상 같은 방식으로 해결할 수 없다는 점을 알게 되었다.

지금까지의 과정 중 가장 어려운 주차였고, 특히 **개념은 이해했는데 실제 코드에서 그 개념이 어디에 해당하는지 연결되지 않은 것**이 가장 큰 어려움이었다.

<br>

### Kafka와 메시징 시스템

Kafka는 이름만 들어봤을 뿐 개념을 전혀 모르는 상태에서 시작했기 때문에, 처음 보는 용어들이 한꺼번에 나와 따라가기 벅찼다.

특히 메시지를 읽어도 지워지지 않는다는 점이 처음에는 받아들이기 어려웠다. 큐라고 하면 꺼내면서 사라지는 자료구조만 떠올렸기 때문이다.

하지만 Kafka를 큐가 아니라 **뒤에 계속 기록하는 장부**로 생각하니, 여러 컨슈머 그룹이 같은 메시지를 각자 읽을 수 있는 이유가 이해되었다.

또한 "같은 그룹은 나눠 읽고, 다른 그룹은 각자 전부 읽는다."는 규칙과, 순서는 파티션 안에서마너 보장되기 때무에 주문 ID를 키로 사용해야 한다는 점도 정리할 수 있었다.

<br>

### Saga 패턴과 보상 트랜잭션

처음에는 보상 트랜잭션이 실패 이전의 모든 단계를 되돌리는 것이라고 생각했다.

하지만 실패한 단계는 이미 로컬 트랜잭션에서 롤백되었고, 조회만 한 단계는 되돌릴 데이터가 없다는 점을 알게 되면서 **보상은 이미 커밋된 단계만, 역순으로 실행한다는** 점을 이해했다.

또한 Saga에는 격리성이 없어서 중간 상태가 외부에 보이기 때문에, 주문의 `PENDING` 상태가 단순한 값이 아니라 아직 확정되지 않았다는 의미를 가진다는 점이 인상 깊었다.

<br>

### DDD와 서비스 경계

도메인 서비스와 응용 서비스, 앤티티와 애그리거트, 포트와 어댑터처럼 이름이 비슷한 개념이 많아 구분하기 어려웠다.

하지만 도메인 서비스는 규칙을 계산하고 응용 서비스는 흐름을 조율한다는 점, 애그리거트는 객체 하나가 아니라 함께 규칙을 지켜야 하는 묶음이라는 점을 기준으로 정리하면서 개념을 나눌 수 있다.

특히 MSA로 서비스를 나눌 때 객체 대신 ID로 참조하는 것이 DDD의 애그리거트 참조 규칙과 같은 이야기라는 점에서, **DDD는 서비스를 어디서 나눌지에 대한 기준**이라는 것을 알게 되었다.

<br>

### Outbox와 멱등성

Outbox 패턴은 처음에 어떤 문제를 해결하는지조차 와닿지 않았다. `@Transactional` 안에서 처리하면 모두 함께 롤백된다고 생각했기 때문이다.

하지만 `@Transactional`은 DB만 묶을 뿐, 이미 Kafka로 발행된 메시지는 되돌릴 수 없다는 점을 이해하면서 Dual Write 문제를 알게 되었다.

Outbox는 **두 시스템에 쓰는 문제를 하나의 DB에 쓰는 문제로 바꾸는 방법**이고, 유실은 막지만 중복은 막지 못하기 때문에 멱등한 컨슈머와 항상 함께 사용해야 한다는 점도 정리할 수 있었다.

<br>

### Prometheus와 Grafana

Micrometer, Actuator, Prometheus, Grafana가 한꺼번에 등장하면서 매트릭이 어디서 만들어지고 어디서 저장되는지 헷갈렸다. 처음에는 Grafana가 데이터를 저장한다고 생각하기도 했다.

하지만 **앱은 현재 값을 공개하고, Prometheus는 주기적으로 가져가 저장하며, Grafana는 조회해서 그래프로 보여준다**는 역할을 구분하면서 전체 구조를 이해할 수 있었다.

또한 코드의 `orders.created`가 Prometheus에서 `orders_created_total`로 바뀌는 것처럼, 이름 변환 규칙을 알고 나서야 코드와 쿼리가 연결되었다.

<br>

개념 위주로만 공부하다 보니, 수업 코드를 보면 각 클래스가 무슨 역할을 하는지 여전히 연결되지 않았다.

그래서 주문 서비스와 결제 서비스가 Kafka로 통신하는 작은 예시 프로젝트를 직접 타이핑하며 작성해 보았다.

`KafkaTEmplate.send()`로 보내는 코드와 `@KafkaListener`로 받는 코드가 메서드 호출이 아니라 **토픽 이름으로 연결된다**는 점을 직접 확인하면서, 따라가기 어려웠던 이유를 이해할 수 있었다.

특히 주문 → 결제 → 결좌 → 주문 상태 변경 또는 보상으로 이어지는 흐름을 순서대로 작성해 보니, 개념으로만 알고 있던 Saga와 보상 트랜잭션이 실제 코드에서 어떻게 구현되는지 연결되었다.

앞으로는 개념을 정리하는 데서 그치지 않고, **작은 예제라도 직접 작성하고 실행해 보면서 개념이 코드의 어느 부분에 해당하는지 연결하는 습관**을 가져야겠다.
