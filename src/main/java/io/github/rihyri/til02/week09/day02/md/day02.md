# Week 09 - Day 02. 모놀리틱 분해와 DDD

<br>

오늘 수업은 두 부분으로 나뉜다.

1. **1일차에 이어서 :** 실제 모놀리틱 쇼핑몰을 user / product / order 세 서비스로 쪼개면 코드와 DB가 어떻게 바뀌는가
2. **DDD (도메인 주도 설계) :** 서비스를 "어디서" 자르고, 자른 서비스 "안"의 코드를 어떻게 짜는가


두 내용은 하나로 이어진다. 1일차에서 MSA에서 가장 어려운 질문이 **"어디를 기준으로 자를 것인가"** 라고 했는데, 그 질문에 대한 답이 DDD다.

```aiignore
[1일차]  서비스를 나누면 → 메시지로 대화하고 → Saga로 데이터를 맞춘다
[2일차]  어디서 나눌까?  → DDD 전략적 설계 (바운디드 컨텍스트)
         나눈 안쪽은?    → DDD 전술적 설계 (엔티티, VO, 애그리거트 …)
         패키지는?       → 4계층 아키텍처
```

### 1.3 세 서비스가 주고받는 이벤트 흐름

1일차에 배운 Choreography Saga가 실제로 실제 코드에서 어떻게 배치되는지 정리하면 다음과 같다. 각 서비스는 **자기 토픽에 발행하고, 필요한 다른 토픽을 구독한다.**

```aiignore
order-api   ──ORDER_CREATED──────────────>  [order-event]
                                                 │ 구독
user-api    <────────────────────────────────────┘
user-api    ──USER_VALIDATED / 실패──────>  [user-event]
                                                 │ 구독 (성공이면 product, 실패면 order)
product-api <────────────────────────────────────┤
product-api ──PRODUCT_RESERVED / 실패────>  [product-event]
                                                 │ 구독
order-api   <────────────────────────────────────┘  → COMPLETED 또는 CANCELLED(보상)
```

<table>
    <thead>
        <th>서비스</th>
        <th>하는 일</th>
        <th>발행</th>
        <th>구독</th>
    </thead>
    <tbody>
        <tr>
            <td>user-api</td>
            <td>주문자 검증</td>
            <td>user-event</td>
            <td>order-event</td>
        </tr>
        <tr>
            <td>product-api</td>
            <td>재고 차감</td>
            <td>product-event</td>
            <td>user-event</td>
        </tr>
        <tr>
            <td>order-api</td>
            <td>Saga 시작과 마무리, 실패 시 보상</td>
            <td>order-event</td>
            <td>user-event, product-event</td>
        </tr>
    </tbody>
</table>

order-api가 user-event를 구독하는 이유는 **사용자 검증 실패 시 바로 주문을 취소(보상)** 하기 위해서다.

<table>

        </tr>
        <tr>
            <td>enable.idempotence=true</td>

            <td>중복 기록을 막는 것은 이 설정이다. 기본값 true</td>
        </tr>
        <tr>
            <td>group-id</td>
            <td>이 컨슈머가 속한 컨슈머 그룹 이름</td>
            <td>애플리케이션 이름을 그대로 써서 서비스마다 그룹이 따로 생긴다.</td>
        </tr>
        <tr>
            <td>auto-offset-reset=earliest</td>
            <td>커밋된 오프셋이 없거나 서버에서 사라졌을 때 어디서부터 읽을지</td>
            <td>❗"만료 처리"보다 넓은 의미다. earliest는 맨 처음부터, latest는 최신부터. 기본 값은 latest</td>
        </tr>
    </tbody>
</table>

`group-id`를 서비스 이름으로 두는 것이 1일차 내용과 연결된다. **서비스마다 그룹이 다르므로 각 서비스가 같은 이벤트를 각자 전부 받는다.** 같은 서비스를 여러 대 띄우면 같은 그룹이 되어 파티션을 나눠 갖는다.

`earliest`로 두는 이유도 생각해 볼 만하다. 서비스가 처음 뜰 때 커밋된 오프셋이 없는데 `latest(기본값)`이면 **서비스가 뜨기 전에 쌓인 이벤트를 건너뛴다.** Saga 이벤트를 놓치면 주문이 영원히 PENDING에 머물 수 있으므로 처음부터 읽게 한 것이다.

## 2. DDD 처음 이해하기

<br>

### 2.1 DDD를 한 문장으로

DDD(Domain-Driven-Design)는 **기술이 아니라 비즈니스 문제를 중심으로 설계하자**는 방법론이다.

지금까지 설계를 시작할 때 보통 "테이블부터 그리고, 컨트롤 / 서비스 / 매퍼를 만든다"는 순서였다. DDD는 순서를 뒤집는다. **"이 사업은 무슨 일을 하고, 어떤 규칙이 있는가"** 를 먼저 정리하고, 그 규칙을 그대로 코드로 옮긴다.

### 2.4 왜 MSA에 DDD가 필요한가?

- **서비스 경계를 정하는 기준이 된다.** DDD의 바운디드 컨텍스트가 마이크로서비스를 나누는 가장 좋은 출발점이다.
- **비즈니스 변경이 코드 변경으로 바로 이어진다.** 규칙과 코드의 이름이 같으므로 "할인 정책이 바뀌었다"고 하면 고칠 곳이 바로 보인다.

### 3.2 바운디드 컨텍스트 (Bounded Context)

Microsoft 문서의 정의는 **"특정 도메인 모델이 적용되는 경계"** 다. 경계 안에서는 하나의 단어가 **딱 하나의 의미**로만 쓰인다.

같은 "상품"이라도 맥락마다 필요한 정보가 완전히 다르다.

<table>
    <thead>
        <th>컨텍스트</th>
        <th>"상품"에 필요한 정보</th>
    </thead>
    <tbody>
        <tr>
            <td>전시</td>
            <td>상품명, 이미지, 설명, 판매가</td>
        </tr>
        <tr>
            <td>재고</td>
            <td>바코드, 창고 위치, 실제 수량</td>
        </tr>
        <tr>
            <td>배송</td>
            <td>무게, 부피, 파손 주의 여부</td>
        </tr>
    </tbody>
</table>

이 셋을 하나의 거대한 `Product` 클래스에 다 넣으면, 배송 담당자가 무게 필드를 바꿨는데 전시 화면이 깨지는 일이 생긴다. **각 컨텍스트가 자기에게 필요한 "상품" 모델을 따로 가지는 것**이 바운디드 컨택스트의 핵심이다.

- 이상적으로 **하나의 컨텍스트를 한 팀이 맡고, 코드 저장소와 DB도 따로** 가진다.
- 컨텍스트와 서비스는 보통 1:1로 대응하지만 꼭 그런 것은 아니다. Microsoft 문서는 DDD가 반복적인 과정이라 **서비스 경계는 고정되지 않고** 나중에 더 잘게 나뉠 수 있다고 말한다.

<br>

### 3.3 컨텍스트 맵 (Context Map)

컨텍스트를 나누기만 하면 시스템이 돌아가지 않는다. 주문은 상품 가격을 알아야 하고, 배송은 주문 정보를 받아야 한다. **컨텍스트끼리 어떤 관계로 데이터를 주고받는지 그린 지도**가 컨텍스트 맵이다.

관계를 읽을 때는 **업스트림 / 다운스트림**을 먼저 구분한다. 강물이 위에서 아래로 흐르듯, 영향이 흐르는 방향이다.

- **업스트림 (Upstream) :** 데이터를 제공하고 변경의 주도권을 가진 쪽
- **다운스트림 (DownStream) :** 그 데이터를 받아 쓰고, 업스트림이 바뀌면 영향을 받는 쪽

```aiignore
       [상품] (업스트림)
        │          │
        ▼          ▼
     [주문]      [배송]   (다운스트림)
```

## 4. 전술적 경계 : 경계 안의 코드 짜기

<br>

### 4.1 엔티티 (Entity)와 밸류 오브젝트 (Value Object)

도메인 모델을 이루는 가장 기본 재료다. 구분 기준은 **식별자(ID)가 있는가, 값이 바뀔 수 있는가** 두 가지다.

<table>
    <thead>
        <th>질문</th>
        <th>엔티티</th>
        <th>밸류 오브젝트 (VO)</th>
    </thead>
    <tbody>
        <tr>
            <td>같은지 무엇으로 판단하나</td>
            <td>ID가 같으면 같다.</td>
            <td>모든 값이 같으면 같다.</td>
        </tr>
        <tr>
            <td>값이 바뀌면</td>
            <td>같은 객체의 상태가 바뀐 것</td>
            <td>새 객체로 통째로 교체한 것</td>
        </tr>
        <tr>
            <td>비유</td>
            <td>사람 (이름, 주소가 바뀌어도 주민번호가 같으면 같은 사람)</td>
            <td>만 원짜리 지폐 (어느 지폐든 만 원이면 똑같다)</td>
        </tr>
        <tr>
            <td>예시</td>
            <td>주문, 회원</td>
            <td>금액, 주소, 기간</td>
        </tr>
    </tbody>
</table>

<br>

#### · 엔티티를 만들 때
- **생명주기**가 있다. 주문이 PENDING에서 COMPLETED로 바뀌어도 ID가 같으면 같은 주문이다.
- **setter로 열지 않는다.** 상태 변경은 `취소하기`, `확정하기`처럼 **비즈니스 의도가 드러나는 메서드**로만 허용하고, 그 안에서 "PENDING일 때만 취소 가능" 같은 규칙을 검사한다.
- Microsoft 문서는 비즈니스 로직이 엔티티 밖(서비스 클래스)에 있으면 엔티티가 데이터만 담는 껍데기가 된다고 경고하며, 이를 **빈약한 도메인 모델(Anemic Domain Model)** 이라고 부른다.

#### · VO를 만들 때
- **불변**이다. 값을 바꾸고 싶으면 새 VO를 만든다. 자바의 `String`, `BigDecimal`이 대표적인 VO다.
- 값이 같으면 같은 객체로 취급해야 하므로 `equals()`와 `hasCode()`를 **값 기준**으로 정의한다. Java 16 이상의 `record`를 쓰면 불변성과 값 비교를 자동으로 얻는다.
- **생성할 때 스스로 검증한다.** 예를 들어 금액 VO는 음수가 들어오면 생성 자체를 거부한다.
- Microsoft 문서는 **"VO를 기본 선택으로 삼고, 시간에 따라 추적해야 할 때만 엔티티로 올려라"** 고 권한다.

<br>

#### · 원시 타입 대신 VO를 쓰면 좋은 점

총액을 `BigDecimal`로 두면 음수가 들어가거나, 실수로 수량과 금액을 더하는 코드도 문제없이 컴파일된다. `Money` 같은 VO로 감싸면 **잘못된 값은 만들어지지 않고, 금액 계산 규칙도 한 곳에 모인다.**

<br>

### 4.2 애그리거트 (Aggregate)

전술적 설계에서 가장 중요한 개념이다.

**애그리거트 = 항상 함께 일관성을 지켜야 하는 엔티티와 VO의 묶음**이다. Microsoft 문서 표현으로는 **일관성 경계(consistency boundary)** 다.

```aiignore
 ┌──────────── 주문 애그리거트 ────────────┐
 │                                         │
 │   Order (애그리거트 루트, 엔티티)       │  ← 외부는 여기로만 접근
 │     ├── OrderLine (주문 상품, 엔티티)   │
 │     ├── ShippingAddress (배송지, VO)    │
 │     └── Money (총액, VO)                │
 │                                         │
 │   userId  ─── ID로만 → [회원 애그리거트] │
 └─────────────────────────────────────────┘
```

**애그리거트 루트**는 묶음의 대표이자 **문지기**다. 외부 객체는 루트를 통해서만 안쪽 요소에 접근할 수 있다. 그래서 "묶음 안의 데이터는 항상 규칙에 맞는 상태"라는 것을 혼자 책임질 수 있다.

#### · 애그리거트 설계 규칙 4가지

<table>
    <thead>
        <th>규칙</th>
        <th>이유</th>
    </thead>
    <tbody>
        <tr>
            <td>① 루트를 통해서만 변경한다.</td>
            <td>배송지를 바꾸려면 배송지를 직접 고치지 않고 주문에게 "배송지 바꿔줘"라고 시킨다. 그래야 "PENDING일 때만 변경 가능" 규칙을 한 곳에서 지킨다.</td>
        </tr>
        <tr>
            <td>② 한 트랜잭션에는 애그리거트 하나만 수정한다.</td>
            <td>여러 개를 바꿔야 하면 하나를 바꾼 뒤 도메인 이벤트로 나머지를 바꾼다. (최종적 일관성) 1일차 Saga와 같은 원리다.</td>
        </tr>
        <tr>
            <td>③ 다른 애그리거트는 ID로만 참조한다.</td>
            <td>주문은 회원 객체가 아니라 회원 ID를 가진다. 객체로 얽혀 있지 않아야 나중에 서비스로 떼어낼 수 있다.</td>
        </tr>
        <tr>
            <td>④ 작게 만든다.</td>
            <td>크면 여러 사용자가 동시에 수정할 때 충돌이 잦고 조회 비용도 크다.</td>
        </tr>
    </tbody>
</table>

<br>

### 4.3 리포지터리 (Repository)

애그리거트를 저장하고 꺼내는 일을 **컬렉션처럼 추상화한 인터페이스**이다.

- **애그리거트 루트마다 하나만** 만든다. 주문 리포지토리는 있지만 주문 상품 리포지터리나 배송지 리포지터리는 만들지 않는다. 안쪽 요소는 주문과 함께 저장되고 함께 조회되어야 묶음의 규칙이 깨지지 않는다.
- **인터페이스는 도메인 계층, 구현은 인프라 계층**에 둔다.
- 그래서 저장 기술을 JPA에서 MyBatis로 바꿔도 도메인 코드는 바뀌지 않는다.

<br>

### 4.4 도메인 서비스 vs 응용 서비스

이름이 둘 다 "서비스"라서 헷갈리기 쉽다.

<table>
    <thead>
        <th>구분</th>
        <th>도메인 서비스</th>
        <th>응용 서비스</th>
    </thead>
    <tbody>
        <tr>
            <td>하는 일</td>
            <td>엔티티 하나에 넣기 애매한 비즈니스 규칙 계산</td>
            <td>유스케이스의 흐름 조율</td>
        </tr>
        <tr>
            <td>아는 것</td>
            <td>도메인 객체만</td>
            <td>트랜잭션, 리포지터리, 포트</td>
        </tr>
        <tr>
            <td>모르는 것</td>
            <td>DB, HTTP, 트랜잭션</td>
            <td>비즈니스 규칙 (도메인에 맡김)</td>
        </tr>
        <tr>
            <td>비유</td>
            <td>회사의 사내 규정집</td>
            <td>규정을 보고 일을 진행하는 담당자</td>
        </tr>
        <tr>
            <td>예시</td>
            <td>배송비 정책 ("3만원 이상 무료 배송")</td>
            <td>주문 생성 서비스</td>
        </tr>
    </tbody>
</table>

**도메인 서비스가 필요한 순간 :** "이 로직을 주문에 넣기도 애매하고 상품에 넣기도 어색한데?" 싶을 때다. 배송비 기준은 주문 하나의 속성이 아니라 **회사의 정책**이다. 정책이 바뀌어도 주문 코드는 그대로야 하므로 따로 뺀다.

Microsoft 문서도 응용 서비스는 **도메인 서비스와 리포지토리 호출을 조율하고 트랜잭션을 관리하되, 비즈니스 로직 자체는 갖지 않는다**라고 설명한다.

외부 API 호출처럼 기술이 필요한 일은 도메인 서비스에 넣지 않고, 응용 계층의 **포트(인터페이스)** 로 추상화한다.

<br>

### 4.5 도메인 이벤트 (Domain Event)

**도메인에서 일어난 의미 있는 사실**을 표현한 객체다. 1일차의 "명령이 아니라 사실을 알린다"와 같은 개념이 서비스 안쪽까지 들어온 것이다.

- 이름은 **과거형**, 객체는 **불변**으로 만든다. (주문됨, 주문 취소됨)
- Microsoft 문서는 "행이 하나 추가됐다"는 도메인 이벤트가 아니고 **"배송이 취소됐다"처럼 비즈니스적으로 의미 있는 변화**여야 한다고 설명한다.
- 주문은 "취소됐다"는 사실만 기록하고, **환불, 알림, 통계는 이벤트를 받은 쪽이 처리**한다.

#### · 이벤트 흐름

```aiignore
① 애그리거트     : 상태가 바뀔 때 이벤트를 안에 모아 둔다.
② 응용 서비스    : 저장한 뒤 모아 둔 이벤트를 꺼내서 발행한다.
③ 인프라 핸들러   : 트랜잭션이 커밋된 뒤에 이벤트를 처리한다.
```

③에 쓰인 Spring의 `@TransactionalEventListener`는 리스너를 **트랜잭션의 특정 단계에 묶는다.** Spring 공식 문서 기준으로 정리하면 다음과 같다.

<table>
    <thead>
        <th>단계 (phase)</th>
        <th>언제 실행되나</th>
    </thead>
    <tbody>
        <tr>
            <td>BEFORE_COMMIT</td>
            <td>커밋 직전</td>
        </tr>
        <tr>
            <td>AFTER_COMMIT (기본값)</td>
            <td>커밋이 성공한 뒤</td>
        </tr>
        <tr>
            <td>AFTER_ROLLBACK</td>
            <td>롤백한 뒤</td>
        </tr>
        <tr>
            <td>AFTER_COMPLETION</td>
            <td>커밋이든 롤백이든 끝난 뒤</td>
        </tr>
    </tbody>
</table>

- **커밋 후에 처리하는 이유 :** 주문 저장은 롤백됐는데 "주문 취소됨" 알림이 먼저 나가는 일을 막기 위해서이다.

공식 문서에는 하나 더 주의할 점이 있다. **실행 중인 트랜잭션이 없으면 리스너가 아예 호출되지 않는다.**(`fallbackExecution = true`로 바꿀 수 있다.) 트랜잭션 밖에서 이벤트를 발행했는데 아무 일도 안 일어난다면 이것부터 의심하면 된다.

3일차에는 이 핸들러 자리를 **Outbox + Kafka 발행**으로 바꿔 다른 서비스로 이벤트를 보낸다고 한다. Microsoft 문서도 서비스 경계를 넘을 때는 **원래 트랜잭션이 커밋된 뒤 메시지 브로커가 비동기 발행**한다고 설명한다.

#### · 이벤트 스토밍 (Event Storming)

도메인 이벤트는 코드보다 **설계 단계에서 먼저 찾는다.** 기획자와 개발자가 함께 벽에 "무슨 일이 일어났는가"를 과거형 이벤트로 붙여 나가고, 그 이벤트를 일으키는 명령, 이벤트를 가진 애그리거트, 경계를 찾아내는 워크숍 방식이다.

## 5. DDD 4계층 아키텍처

<br>

### 5.1 왜 패키지 구조를 바꾸나

1일차 코드는 controller / service / repository / model 처럼 **기술 기준**으로 나눴다. 이렇게 하면 비즈니스 규칙이 서비스 클래스 여기저기에 흩어지기 쉽다. DDD는 **책임 기준**으로 네 계층을 나눈다.

<table>
    <thead>
        <th>계층</th>
        <th>책임</th>
        <th>들어가는 것</th>
        <th>알면 안 되는 것</th>
    </thead>
    <tbody>
        <tr>
            <td>presentation (표현)</td>
            <td>HTTP 요청을 응용 서비스 호출로 번역하고, 결과를 응답으로 반환</td>
            <td>컨트롤러, 요청/응답 DTO, 예외 → HTTP 상태 변환</td>
            <td>비즈니스 규칙, JPA</td>
        </tr>
        <tr>
            <td>application (응용)</td>
            <td>유스케이스 흐름 조율</td>
            <td>응용 서비스, Command, 외부 조회용 포트 인터페이스</td>
            <td>HTTP, 구체적인 저장 기술</td>
        </tr>
        <tr>
            <td>domain (도메인)</td>
            <td>비즈니스 규칙과 상태</td>
            <td>애그리거트, 엔티티, VO, 도메인 서비스, 도메인 이벤트, 리포지터리 인터페이스</td>
            <td>Spring MVC, Kafka, HTTP</td>
        </tr>
        <tr>
            <td>Infrastructure</td>
            <td>기술 구현</td>
            <td>JPA 리포지터리 구현체, 외부 서비스 호출 구현체, 이벤트 핸들러</td>
            <td>(다른 계층의 인터페이스를 구현하는 역할)</td>
        </tr>
    </tbody>
</table>

Microsoft의 .NET 마이크로서비스 가이드는 표현과 응용을 합쳐 3계층(응용, 도메인, 인프라)으로 설명한다. 나누는 개수는 달라도 **도메인 계층이 중심이고 아무것도 의존하지 않는다**는 원칙은 같다.

<br>

### 5.2 의존성 규칙과 의존성 역전 (DIP)

**의존성은 항상 바깥에서 안쪽(도메인)을 향한다.** 도메인은 가장 안정적이어야 하므로 아무것도 의존하지 않는다.

그런데 여기서 모순이 생긴다. 주문을 DB에 저장하려면 JPA가 필요한데, 도메인이 JPA를 의존하면 규칙이 깨진다.

해결 방법은 **화살표 방법을 뒤집는 것**이다.

```aiignore
[뒤집기 전]   도메인 ──의존──> JPA 구현             (도메인이 기술을 앎 ❌)

[뒤집은 후]   도메인: "이런 저장소가 필요해" (인터페이스 = 포트)
                 ▲
                 │ 구현
              인프라: JPA로 만든 구현체 (어댑터)     (기술이 도메인을 앎 ✅)
```

- **포트 (Port) :** 안쪽이 정의한 인터페이스. 콘센트 구멍에 해당한다.
- **어댑터 (Adapter) :** 바깥이 만든 구현체. 콘센트에 꽂는 플러그에 해당한다.

<br>

    <thead>
        <th>포트 (안쪽)</th>
        <th>어댑터 (인프라)</th>
    </thead>
    <tbody>
        <tr>
            <td>도메인의 주문 리포지토리 인터페이스</td>
            <td>JPA로 구현한 주문 리포지터리 어댑터</td>
        </tr>
        <tr>
            <td>응용 계층의 상품 조회포트</td>
            <td>지금은 메모리 임시 구현, 나중에 실제 상품 서비스 호출</td>
        </tr>
    </tbody>
</table>


상품 조회 포트는 3.3의 **ACL(번역 계층)** 역할도 한다. 상품 서비스가 어떤 모델을 쓰든 주문 쪽은 자기에게 필요한 값(상품 ID, 이름, 가격)만 받는다.

Microsoft 문서에서도 **"응용은 도메인과 인프라에, 인프라는 도메인에 의존하지만 도메인은 어느 계층에도 의존하지 않는다."**, 그리고 도메인은 **저장 방식을 완전히 몰라야 한다.(Persistence Ignorance)**고 설명한다.

<br>

### 5.3 주문 생성 요청 하나가 계층을 지나는 흐름

```aiignore
POST /api/orders
   │
   ▼
[표현]   요청 DTO 검증 → 응용 서비스용 Command로 변환
   │
   ▼
[응용]   트랜잭션 시작
         ├─ 상품 조회 포트로 상품 정보 가져오기
         ├─ 상품 금액 합계 계산
         ├─ 도메인 서비스(배송비 정책)로 배송비 계산
         ├─ 도메인에게 "주문 만들어줘"
   │     │
   ▼     ▼
[도메인] 규칙 검사 : 주문 상품이 1개 이상인가?
         총액 = 상품 합계 + 배송비, 상태 = PENDING
   │
   ▼
[응용]   리포지토리로 저장 → 주문 ID 생성
         → "주문됨" 이벤트 기록 → 이벤트 발행
   │
   ▼
[인프라] 커밋 후 이벤트 핸들러 실행
   │
   ▼
[표현]   도메인 객체를 응답 DTO로 변환해서 201 Created 반환
```

**저장 후에 이벤트를 기록하는 이유 :** 저장해야 DB에서 주문 ID가 생기고, 그 ID를 이벤트에 담을 수 있기 때문이다.

## 6. 핵심 정리

- 모놀리틱을 쪼개면 DB가 나뉘어 **다른 도메인은 객체가 아니라 ID로만 참조**하고, 존재 확인은 **이벤트로 나중에** 하며, 주문은 **PENDING**에서 시작한다.
- `acks=all`은 **모든 동기화 복제본의 확인**을 기다리는 설정이고, 중복 기록을 막는 것은 `enable.idempotence`다. `auto-offset-reset`은 **커밋된 오프셋이 없거나 사라졌을 때**의 시작 위치다.
- **DDD는 기술보다 비즈니스 규칙을 먼저** 설계한다. 기획과 코드가 같은 언어(유비 쿼티스 언어)를 쓴다.
- **전략적 설계 = 경계 나누기**(바운디드 컨텍스트, 컨텍스트 맵), **전술적 설계 = 경계 안 코드 짜기**(엔티티, VO, 애그리거트 ...)
- 바운디드 컨텍스트 안에서 단어는 **한 가지 의미**만 가진다. 같은 "상품"도 컨텍스트마다 다른 모델이다.
- **엔티티는 ID로, VO는 값으로** 같음을 판단한다. VO는 불변이고 스스로 검증한다.
- **애그리거트는 일관성 경계**다. 루트로만 변경하고, 한 트랜잭션에 하나만 수정하고, 다른 애그리거트는 ID로만 참조하고, 작게 만든다.
- **도메인 서비스는 규칙 계산, 응용 서비스는 흐름 조율**이다.
- `@TransactionalEventListener`의 기본값은 **AFTER_COMMIT**이고, 트랜잭션이 없으면 **호출되지 않는다.**
- 4계층에서 **의존성은 도메인을 향한다.** 도메인이 포트를 정의하고 인프라가 어댑터로 구현한다(DIP). 그래서 **어댑터만 갈아 끼우면** 기술을 바꿀 수 있다.
