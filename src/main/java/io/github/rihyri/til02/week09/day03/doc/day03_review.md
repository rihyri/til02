### Outbox

- **Outbox가 무엇을 해결하는지 문제 자체가 와닿지 않았다.** 평소에는 `@Transcational` 안에서 이것저것 하면 다 같이 롤백된다고 생각했기 때문에, "DB에 저장하고 Kafka로 보내는 것"이 왜 문제인지 처음에는 몰랐다.

- **`@Transcational`은 DB만 묶인다는 것.** Kafka로 이미 나간 메시지는 DB가 롤백되어도 돌아오지 않는다. 그래서 "DB 저장 + Kafka 발행"은 서로 달느 두 시스템에 쓰는 Dual Write가 되고, 어떤 순서로 해도 유실이나 유령 이벤트가 생길 수 있다.

- **Outbox의 핵심은 "두 시스템에 쓰는 문제를 한 시스템에 쓰는 문제로 바꾼 것"이라는 점.** 보낼 이벤트를 같은 DB에 같은 트랜잭션으로 적어 두면 주문과 이벤트 기록은 반드시 함께 저장되거나 함께 사라진다. Kafka로 보내는 것은 릴레이가 나중에 하면 된다. 

<br>

- **Outbox는 유실은 막지만 중복은 막지 못한다.** 릴레이가 발행 직후 상태를 PUBLISHED로 바꾸기 전에 죽으면 같은 이벤트가 다시 나간다. 그래서 **Outbox와 멱등한 컨슈머는 항상 짝**이다. "보내는 쪽은 최소 한 번은 반드시 보내고, 받는 쪽은 두 번 와도 한 번만 기억한다."
- **auto-commit은 처리 완료가 아니라 시간을 기준으로 커밋한다.** 처리 중에 커밋이 먼저 일어나면 유실될 수 있어서 끄고 직접 커밋한다.
- **auto-offset-reset은 "처음 구독할 때만"의미가 있다.** 이미 커밋된 오프셋이 있다면 그 위치부터 읽는다. Kafka의 기본 값은 least라서, 설정하지 않으면 새 그룹은 구독 이전 메시지를 읽지 않는다.
- **PollingPublisher를 여러 인스턴스에서 돌리면 같은 이벤트를 동시에 가져갈 수 있다.**
- **보상 트랜잭션 개수는 "실패 직전까지 무엇이 커밋되었는가"로 정해진다.**
- **"주문 당시 상품명이냐, 현재 상품명이냐"는 기술 문제가 아니라 비즈니스 결정이다.** 그 결정에 따라 스냅샷으로 끝낼지, 이벤트로 복제할지가 달라진다.

<br>

Outbox가 낯설어서 헤맸지만, 이벤트 하나가 태어나서 처리되기까지의 경로를 그려보니 **"보내는 쪽은 Outbox로 반드시 보내고, 받는 쪽은 멱등성으로 한 번만 반영한다."** 는 문장으로 정리할 수 있었다.
