## 어려웠던 점

<br>


### Kafka를 처음 접했다.
Kafka라는 이름만 들어봤지 개념은 전혀 모르는 상태였다. 수업에 처음보는 용어들이 한 번에 쏟아져서 따라기도 벅찼다.

특히 헷갈렸던 것은 두 가지이다.

- **"메시지를 읽어도 지워지지 않는다"는 점** : 지금까지 큐라고 하면 꺼내면 사라지는 자료구조만 생각했기 때문에 처음에는 받아들이기 어려웠다. Kafka를 큐가 아닌 **뒤에만 계속 적는 장부**로 생각하니 이해가 됐다. 지우지 않으니까 재고 서비스, 통계 서비스처럼 여러 그룹이 같은 메시지를 각자 읽을 수 있는 것이다.
- **컨슈머 그룹 안에서와 그룹 사이의 동작 차이** : "같은 그룹은 나눠 읽고, 다른 그룹은 각자 전부 읽는다"는 한 문장으로 정리하고 나서야 감이 왔다. 파티션이 3개인데 컨슈머를 5개 띄우면 2개가 노는 이유도 이 규칙에서 자연스럽게 나온다.

<br>

### Saga 보상 트랜잭션 그림
T1(주문 생성) → T2(사용자 검증) → T3(재고 차감)가 실패하면 C1(주문 취소)로 돌아가는 그림이 처음에는 이해되지 않았다. **"T3에서 실패했는데 왜 재고는 되돌리지 않고 주문만 취소하지?"** 가 의문이었다.

- T2는 조회만 하므로 되돌릴 데이터가 없다.
- T3가 실패했다면 상품 서비스의 로컬 트랜잭션이 이미 롤백되어 재고는 처음부터 줄지 않았다.
- 따라서 실제 커밋되어 남은 변경은 T1뿐이고, 보상도 C1 하나면 된다.

보상 트랜잭션은 모든 단계를 되돌리는 것이 아니라 **"이미 커밋된 간계만, 역순으로"** 되돌리는 것이라는 점을 확실히 알게 되었다.

<br>

### 새롭게 알게 된 것
- **모놀리틱이라고 서버가 1대인 것은 아니다.** 같은 jar를 여러 대 띄울 수 있다. 애플리케이션 종류가 하나라는 뜻이다.
- **MSA가 무조건 정답은 아니다.** 복잡성이 찾아오는 시점이 다를 뿐 두 구조 모두 복잡해진다. 규모가 작을 때 MSA부터 시작하며 손해일 수 있다.
- **이벤트는 명령이 아니라 사실이다.** "재고 줄여줘"가 아니라 "주문이 생성됐다"라고 말해야 새 서비스가 추가되어도 보내는 쪽 코드를 고칠 필요가 없다. 이 규칙이 Choreography Saga의 기반이라는 점도 연결됐다.
- **Kafka의 순서 보장은 파티션 안에서만이다.** 그래서 주문 ID 같은 키를 붙여 주문의 이벤트를 같은 파티션에 보내야 한다.
- **주문의 PENDING 상태는 단순한 상태 값이 아니다.** Saga에는 격리성이 없어 중간 상태가 외부에서 보이는데, PENDING은 "아직 확정되지 않았다"는 표시(Semantic Lock)역할을 한다.

<br>

Kafka를 새롭게 배우게 됐는데 아직 정확하게 이해했다고 말할 수 없다. 계속 복습하면서 익숙해지도록 해야겠다.
