### 이번주에 배운 것
- 클라우드의 서비스 모델과 배포 형태, 그리고 VM과 컨테이너의 차이(OS 격리 vs 커널을 공유하는 프로세스 격리)를 배웠다.

- 컨테이너 로그가 쌓이는 경로, 로크 로테이션, `docker system df`와 prune으로 디스크를 관리하는 방법을 배웠다.

### 헷갈렸던 점

#### 레이어에서 파일을 지워도 이미지가 줄어들지 않는다.

처음에는 Dockerfile 마지막에 `rm`으로 캐시를 지우면 이미지가 작아진다고 생각했다. 실제로는 **레이어는 위에 쌓이기만 하고 아래 레이어를 고칠 수 없어서,** 뒤에서 지운 파일은 가려질 뿐 아래 레이어로 그대로 남는다. 그래서 설치와 정리를 같은 `RUN` 안에서 해야 한다.

#### 같은 Docker 안인데 이름으로 통신이 안 된다.

같은 PC의 Docker에서 띄운 컨테이너라면 당연히 이름으로 찾을 수 있다고 생각했다. 하지만 **기본 bridge 네트워크는 이름 DNS를 제공하지 않고,** `docker network create`로 만든 사용자 정의 네트워크에서만 이름으로 통신할 수 있었다. Compose에서 따로 설정하지 않아도 서비스 이름으로 접속되던 건 Compose가 이 네트워크를 자동으로 만들어 주기 때문이다.

#### 볼륨을 연결했는데 데이터가 사라진다.

볼륨만 연결하면 데이터가 보존된다고 생각했다. 하지만 **앱이 실제로 데이터를 쓰는 경로에 연결해야** 의미가 있다. Redis는 `/data`에 데이터를 쓰는데 다른 경로에 볼륨을 연결하면, 데이터는 엉뚱한 곳에 쌓이고 재시작하면 사라지는 것처럼 보인다.

빈 Volume은 이미지에 있던 파일을 복사해 오고, Bind Mount는 컨테이너 경로를 덮어쓴다는 차이도 처음에는 헷갈렸다.

### 새롭게 알게 된 것
- docker 명령어는 요청만 보낸다. 실제 작업은 Daemon이 하고, 둘은 API로 통신하므로 원격 서버의 Daemon에도 명령을 보낼 수 있다.
- CMD를 shell 형식으로 쓰면 정상 종료가 안 된다. `/bin/sh`가 PID 1이 되어 SIGTERM이 앱까지 전달되지 않는다.
- `latest`는 최신이라는 뜻이 아니다. 태그를 생략했을 때 붙는 기본 이름일 뿐이라 받은 시점마다 내용이 다를 수 있다.
- `1.9` 다음 버전은 `1.10`이다. 시맨틱 버전의 각 자리는 소수점이 아니라 독립된 정수이다.
- `depends_on` 만으로는 준비 완료를 기다리지 않는다. `healthcheck`와 `condition: service_healthy`를 함께 써야 한다.
- `docker logs | grep`은 stderr를 못 찾는다. 파이프는 stdout만 넘기므로 `2>&1`이 필요하다.
- json-file 로그는 크기 제한이 없다. 로테이션을 설정하지 않으면 로그가 디스크를 채운다.

<br>

이번 주 과제를 수행하며 만난 오류(`pull access denied`, 이름으로 안 되는 통신, 사라진 데이터)는 모두 **Docker가 내부에서 어떻게 동작하는지 알면 설명되는 것들**이었고, 그래서 오류가 나면 해결 방법부터 찾기보다 **어떤 동작에서 나온 오류인지 먼저 생각하고 확인 명령으로 좁혀 가는 습관**을 들여야겠다는 결론을 얻었다.
