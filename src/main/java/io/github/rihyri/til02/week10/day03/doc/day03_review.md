### `-p`는 언제 필요한가
처음에는 컨테이너끼리 통신할 때도 포트를 열어 줘야 한다고 생각했다. 그런데 `-p`는 **호스트로 들어온 요청을 컨테이너로 넘겨주는 통로**일 뿐이고, 같은 네트워크 안의 컨테이너끼리는 `db:3306` 처럼 **이름과 컨테이너 포트로 바로 접속**한다. 그림에서 "포트 매핑 불필요"라는 화살표를 보고 정리가 됐다.

그래서 DB 컨테이너에 `-p 3306:3306`을 붙이는 건 **내 PC에서 DB 툴로 접속하고 싶을 때만** 필요한 것이고, 앱 컨테이너가 DB에 붙는 데는 필요 없다. 오히려 열어 두면 외부에서 DB에 접근할 길이 생긴다.


### 기본 bridge에서는 왜 이름으로 안 되나

둘 다 bridge인데 하나는 이름으로 되고 하나는 안 되는게 이상했다. 기본 bridge는 **하위 호안 때문에 이름 DNS를 제공하지 않고,** `docker network create`로 만든 네트워크에서만 Docker 내장 DNS가 동작한다. IP로는 통신되지만 IP는 컨테이너를 다시 만들면 바뀔 수 있어서 설정에 적어둘 수가 없다.

Compose에서 서비스 이름으로 DB에 붙을 수 있었던 것도 Compose가 `프로젝트명_default` 라는 **사용자 정의 bridge** 를 자동으로 만들어 줬기 때문이라는 걸 이번에 알았다.

### Volume과 Bind Mount

둘 다 `-v`로 쓰고 둘 다 데이터를 컨테이너 밖에 두니 같은 것처럼 보였다. 차이는 **누가 위치를 관리하느냐**다. Volume은 Docker가 관리하는 영역에 저장되고, Bind Mount는 내가 지정한 호스트 경로를 그대로 붙인다. `-v` 앞자리가 이름이면 Volume, 경로면 Bind Mount라는 구분법도 알게 됐다.

**"이 파일을 내가 호스트에서 직접 열어 볼 일이 있는가?"** 라는 판단 기준이 가장 기억에 남는다.

<br>
<hr>

- **네트워크도 이미지와 별개인 자원이다.** 이미지와 컨테이너만 정리하면 안 되고 `docker network prune`으로 따로 정리해야 한다.
- **`-p 127.0.0.1:8080:80`처럼 IP를 붙이면 내 PC에서만 접속된다.** 아무것도 안 붙이면 같은 와이파이의 다른 PC에서도 접속할 수 있다는 뜻이기도 하다.
- **컨테이너는 여러 네트워크에 동시에 연결될 수 있다.** Compose에서만 app만 frontend와 backend 양쪽에 연결하고 db는 backend에만 두면, 웹 서버에서 DB로 바로 가는 길을 막을 수 있다.
- **host 모드에서는 `-p`가 무시되고, 같은 이미지로 컨테이너를 여러 개 띄울 수 없다.** 모두 같은 호스트 포트를 쓰려 하기 때문이다.
- **빈 Volume은 이미지 안의 기존 파일을 복사해 오지만, Bind Mount는 경로를 덮어쓴다.** 빈 폴더를 nginx 문서 경로에 Bind Mount하면 기본 페이지가 사라진다.
- **`--user` 만으로는 부족하고 `no-new-privileges`를 함께 써야 한다.** 이미지 안에서 setuid 프로그램이 있으면 일반 사용자도 root가 될 수 있기 때문이다.

<br>

**`-p`는 바깥에서 들어오는 길이고, 컨테이너끼리 같은 네트워크에서 이름으로 만난다**는 것과 **데이터는 컨테이너 밖(Volume)에 둔다**는 두 가지를 잡고 나니, Compose 파일에서 서비스 이름으로 DB에 붙던 이유와 MySQL에 볼륨을 붙이던 이유가 함께 이해됐다.
