# Week 10 - Day 04. 회고

<br>

### 오늘 배운 것
- Docker 가 PID 1의 stdout/stderr를 받아 로그 드라이버로 넘기고, `docker logs`는 호스트에 저장된 로그 파일을 읽는다는 로그 흐름을 배웠다.
- 컨테이너 앱은 로그 파일이 아니라 표준 출력으로 내보내는 것이 원칙이다.
- json-file 로그는 크기 제한이 없어서 `max-size`, `max-file`로 로테이션해야 하고, 운영 서버는 `daemon.js`에 기본 값을 둔다.
- `docker status`로 컨테이너별 자원 사용량을, `docker events`로 컨테이너 이벤트를 확인한다.

<br>

### 새롭게 알게 된 것
- json-file 로그는 앱이 출력한 양보다 2~3배 더 크다. 한 줄마다 `stream`, `time` 같은 정보가 JSON으로 붙기 때문이다.
- nginx 공식 이미지는 로그 파일을 `/dev/stats`, `/dev/stderr`로 심볼릭 링크해 둔다. 파일에만 쓰는 프로그램을 컨테이너 원칙에 맞추는 방법이다.
- `docker logs -f` 중 `Ctrl+C`는 컨테이너를 멈추지 않는다. 로그 보기만 멈춘다.
- `daemon.json`의 로그 기본값은 새로 만든 컨테이너부터 적용된다. 설정만 바꾸고 기존 컨테이너는 그대로라면 여전히 무제한으로 쌓인다.
- 로테이션 크기를 너무 작게 잡아도 문제다. 장애가 났을 때 직전 로그가 이미 지워져 있을 수도 있다.
- json-file 로그는 `docker system df`에 잡히지 않는다. 디스크가 찼는데 df 결과로는 원인이 안 보일 수 있다.
- `docker volume prune -a`는 이름 있는 볼륨까지 지운다. 그리고 Docker 23 이전 버전은 `-a` 없이도 동작한다. 같은 명령이 버전에 따라 위험도가 달라진다.
- `image prune -a`는 롤백용 이전 버전 이미지도 지울 수 있다. 디스크를 비우려다 롤백 수단을 잃을 수 있다.


<br>

로그는 stdout으로 내보내고, Docker가 받아 호스트 파일에 쌓는다는 흐름을 잡고 나니 `docker logs`가 종료된 컨테이너에서도 동작하는 이유와 로그 파일이 디스크를 채우는 이유가 함께 이해됐고, 그래서 로테인션과 prune은 "나중에"가 아니라 처음부터 설정해둘 것이라는 결론을 얻었다.
