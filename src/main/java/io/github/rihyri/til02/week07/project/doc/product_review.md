# Week 07 - Project 회고

<br>

이번 과제는 외부 상품 API를 OpenFeign으로 연동해, 외부 상품을 내부 상품과 함께 'product' 테이블에 통합 저장하는 것이었다.

스케줄러로 매일 자정에 동기화하고, 외부 서저 장애에 대비해 재시도(최대 3회)를 적용했으며, 외부 상품 ID 기준 upsert로 중복 적재를 막았다.

그리고 QueryDSL로 카테고리 · 주문 가능 여부 조건 검색과 페이징을 지원하는 `GET /products` API를 구현했다.

<br>

### 재시도를 "어디에" 걸어야 할까

처음에는 전체 동기화 메서드에 `Retryable`을 붙였는데, 이러면 중간 페이지에서 실패해도 처음부터 데이터를 다시 받게 되었다.

실패 확률이 40%인 서버에서 여러 페이지를 연속으로 성공해야 하니, 재시도를 해도 거의 항상 실패하는 구조였다.

→ 재시도를 페이지 1건 호출 단위로 옮기고, 그 메서드를 별도 클래스(`ExternalProductFetcher`)로 분리했다.

<br>

### 클래스를 왜 나눠야 할까?

`ProductSyncService`, `ProductUpsertService`, `ExternalProductFecther` 등 여러 클래스가 존재한다.

`@Retryable`, `@Transactional`이 프록시 기반이라 같은 클래스 안의 호출에는 적용되지 않기 때문이다.

정리하면, "받아 오기(느리고 실패할 수 있음, 트랜잭션 밖)"와 저장하기(빠르고 전부 아니면 전무, 트랜잭션 안"를 나눈 구조이다.

외부 데이터를 전부 받은 뒤 DB 반영만 하나의 트랜잭션으로 묶는 방식으로 외부 호출을 트랜잭션 안에 오래 두지 않도록 하였다.

스케줄러는 외부 API를 직접 호출하지 않고, "언제 실행할지"만 담당한다.

<br>

이번 과제는 트랜잭션을 어디에서 실행해야 할지, 외부 API를 어떻게 호출하고 불러와서 처리해야 할지 등 많은 고민들을 하게 되었다.

과제를 하면서 어려운 부분이 많았고 아직 완벽하게 이해했다고 말할 수는 없지만 트랜잭션은 백엔드 개발자에게 중요한 역할을 담당한다고 생각하기 때문에 더 공부하여 감을 익혀야 겠다.
