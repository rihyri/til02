# Week 07 - Day 02. 회고

<br>

이번 수업에서는 MySQL의 `EXPLAIN`과 `EXPLAIN ANALYZE`를 통해 쿼리 실행 계획을 확인하고, 인덱스 적용 여부에 따라 데이터 접근 방식이 어떻게 달라지는지 학습했다. 이어서 페이징 처리에서 사용하는 `LIMIT/OFFSET`의 동작을 이해하고, 데이터가 많아질수록 뒤쪽 페이지 조회 비용이 커지는 이유와 Keyset Pagination을 통한 개선 방법도 정리했다.

<br>

가장 인상 깊었던 부분은 **인덱스가 존재한다고 해도 빠른 쿼리가 완성되지 않는다**라는 점이다. 실행 계획의 `type`, `key`, `rows`, `Extra`를 함께 살펴보고, 검색 조건의 범위와 실제 데이터 분포까지 고려해야 인덱스의 효과를 판단할 수 있었다. 또한 `eq_ref`는 JOIN 과정에서 이전 테이블의 각 행에 대해 고유 인덱스로 한 행을 찾는 접근이고, `const`는 상수 조건에서 쿼리 전체의 한 행이 결정되는 접근이라는 차이를 이해했다.

페이징에서도 `LIMIT 10`으로 결과를 10건만 반환한다고 해서 DB가 반드시 10건만 읽는 것은 이나리는 것도 알게 되었다. `OFFSET`이 커지면 앞쪽 데이터를 건너뛰기 위해 많은 행을 처리해야 하는 반면, Keyset Pagination은 마지막으로 본 정렬 키를 이용해 다음 범위를 조회할 수 있다.

<br>

`EXPLAIN`의 접근 방식이 항상 예상과 일치하지 않는다는 부분이 어려웠다. 예를 들어 인덱스를 추가하더라도 조건에 맞는 행이 대부분이라면 옵티마이저가 전체 스캔을 선택할 수 있다는 점을 구분해야 했다. 또 `created_at`처럼 중복될 수 있는 값을 커서로 사용하면 페이지 경계에서 누락이 발생하기 때문에, `id`를 보조 정렬 키로 함께 사용해야 한다는 점도 주의할 부분이다.

<br>

쿼리 최적화는 인덱스를 무조건 추가하는 일이 아니라, 실행 계획을 근거로 실제로 읽는 데이터를 줄이는 과정이라는 것을 배웠다.

앞으로 조회 API를 구현할 때는 단순히 SQL이 정상 실행되는지만 확인하지 않고, **실제 실행 계획과 정렬 순서, 인덱스, 데이터 규모**를 함께 점검해야겠다. 또한 INSERT와 SELECT 가 모두 많은 테이블일 때 INDEX를 어떻게 처리하면 좋을지 고민도 많이 해봐야 할 것 같다.
