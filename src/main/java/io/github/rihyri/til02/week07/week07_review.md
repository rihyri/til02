# Week 07 - 학습 및 프로젝트 회고

<br>

7주차에는 MySQL 인덱스 설계와 쿼리 최적화, 트랜잭션 전파 옵션, 외부 API 연동 및 재시도 처리에 대해 학습했다.

이전까지는 데이터베이스에서 원하는 데이터를 조회하고, `@Transactional`을 이용해 여러 작업을 하나의 트랜잭션으로 처리하는 방법에 집중했다.

하지만 이번 수업에서는 같은 기능을 구현하더라도 인덱스 설계에 따라 조회 성능이 달라질 수 있고, 트랜잭션의 전파 옵션과 예외 처리 방식에 따라 데이터 저장 결과도 달라질 수 있다는 점을 알게 되었다.

특히 기능이 정상적으로 동작하는 것 뿐만 아니라 **성능과 예외 상황까지 고려하여 설계하는 것이 중요하다**는 점이 인상 깊었다.

<br>

### 인덱스 설계와 실행 계획

이번 주에는 B-Tree 구조를 학습하며 인덱스가 데이터를 빠르게 탐색할 수 있는 원리를 이해했다.

처음에는 인덱스를 생성하면 무조건 조회 성능이 향상된다고 생각했지만, 실제로는 데이터의 분포와 검색 조건, 인덱스 컬럼의 순서에 따라 성능이 달라진다는 점을 알게 되었다.

특히 복합 인덱스의 `Leftmost Prefix` 규칙과 `EXPLAIN`을 활용한 실행 계획 분석이 기억에 남았다.

단순히 인덱스를 생성하는 것에서 끝나는 것이 아니라, **실제로 어떤 인덱스가 사용되고 있는지 확인하는 과정**이 필요하다는 점을 배웠다.

<br>

### 페이징 쿼리와 최적화

`OFFSET/LIMIT`와 `Keyset Pagination`의 차이도 새롭게 알게 되었다.

기존에는 페이징을 구현할 때 `OFFSET`을 사용하는 것이 자연스럽다고 생각했지만, 데이터가 많아지고 뒤쪽 페이지를 조회할수록 불필요하게 읽는 데이터가 증가할 수 있다는 점을 이해했다.

`Keyset Pagination`은 마지막으로 조회한 데이터를 기준으로 다음 범위를 탐색하기 때문에 대량 데이터 조회에 유리할 수 있다는 점이 흥미로웠다.

<br>

### 트랜잭션 전파 옵션

이번 주에 가장 이해하기 어려웠던 내용은 트랜잭션 전파 옵션이었다.

각 전파 개념을 이해하는 것은 어렵지 않았지만, 부모와 자식 메서드에서 예외가 발생했을 때 실제로 어떤 데이터가 커밋되고 롤백되는지 구분하는 과정이 복잡하게 느껴졌다.

특히 `REQUIRES_NEW`는 독립적인 트랜잭션을 생성하는 반면, `NESTED`는 SAVEPOINT를 이용하여 부분 롤백을 수행한다는 차이를 이해하는 것이 중요했다.

또한 `@Async`를 사용하면 별도 스레드에서 작업이 실행되기 때문에 기존 트랜잭션이 자동으로 전달되지 않는다는 점도 새롭게 배웠다.

아직 여러 전파 옵션이 조합된 복잡한 상황을 이해하긴 어려웠지만, **트랜잭션의 경계와 실행 흐름을 먼저 파악하는 것이 중요하다**는 점을 알게 되었다.

<br>

### 외부 상품 데이터 동기화

외부 상품 API를 연동하고, 가져온 데이터를 내부 상품 테이블에 저장하는 기능을 구현했다. 

외부 API는 네트워크 상태나 서버 문제로 인해 호출에 실패할 수 있기 때문에 재시도 전략이 필요했다. 

Spring Retry의 `@Retryable`을 활용하면 특정 예외가 발생했을 때 정해진 횟수만큼 작업을 다시 시도할 수 있다는 점을 학습했다.

처음에는 재시도 횟수만 설정하면 된다고 생각했지만, 실제로는 이미 저장된 데이터가 다시 처리될 가능성과 트랜잭션 롤백 범위까지 고려해야 한다는 점을 알게 되었다.

<br>

이번 7주차에는 데이터베이스 조회 성능과 트랜잭션의 동작 원리르 조금 더 깊이 이해할 수 있었다.

특히 인덱스와 실행 계획을 학습하면서 SQL이 정상적으로 실행되는 것과 효율적으로 실행되는 것은 다르다는 점을 알게 되었다.

또한 외부 API 연동에서는 데이터를 정상적으로 저장하는 것뿐 아니라, 중복 요청이나 호출 실패가 발생하더라도 데이터의 일관성을 유지하는 것이 중요하다고 느꼈다.

아직 트랜잭션 전파와 비동기 처리의 세부 동작은 추가적인 실습이 필요하지만, 앞으로 기능을 구현할 때 **정상 동작뿐 아니라 성능과 예외 상황까지 함께 고려하는 습관**을 가져야겠다.
